Rook SuperAgent 设计草案

参考 dsh-superagent-prototype，给 Rook 增加一个自动回答问题、接下游开发的 Agent。草案阶段，尚未实现。

TL;DR

Rook 已有 prototype 领域模型的大半：Kanban Task 对应 Ticket，Run 对应 Executor，Task 时间线对应 Channel。缺两个实体：用户创建的智能体定义，以及 Task 到 Session 的绑定。阶段 0 先做智能体定义，阶段 1 做「评论里 @智能体 自动回答」，阶段 2 接单开发，阶段 3 才建 Durable Inbox 和外部事件。常驻 Agent 文章的五个原语里，收件箱、定时器、权限已有对应物，阶段 1 复用持久的 Queue，不新建收件箱表。记忆和发件箱各有一个缺口。

与 prototype 的对照

prototype 的链路是 Source → Trigger → Thread → Eval → Ticket → Assignment → Executor。下表说明每一环在 Rook 里有没有现成的对应物。

prototypeRook 现状缺口
TicketKanban Task：状态、接单人、交付、验收、Agent 凭据无
Executor聊天管理器产生的 Run，自动化投递已走这条路Task 到 Session 的绑定
ChannelTask 时间线的 activity，作者 Rook无
SourceTask 评论，已能解析邮箱 mention解析 @Rook
Gate用户准入加默认组 RD触发者检查
Report交付、提问、run_finished状态映射
Durable Inbox、Worker、Scheduler无，词表标为后续阶段 3
Eval 研判、Mandate、Policy 版本无阶段 1、2 不做
为什么不照搬 Ticket 和 Mandate

Task、接单操作和 Agent 凭据已经承担授权。再加一套 Ticket、Mandate 会让同一件事有两个名字。阶段 1 只响应显式的 @Rook，不需要模型判断「这条消息是不是在要活」。

常驻 Agent 的五个原语

文章把常驻 Agent 拆成收件箱、定时器、记忆、权限、发件箱。下表对照 Rook 现状。依据是用户提供的文章原文（Anthropic，2026-11-13）。

原语文章的要求Rook 现状缺口
事件收件箱所有来源先写事件，再由 worker 取；按来源标识去重；每个收件箱一个活跃 worker；连续消息合并成一次运行每个 Session 有持久化的 Queue，按 requestId 幂等，创建 Run 的事务内取出队首，自动化投递已能把多条合并成一次 Turn外部 webhook 没有入口，留给阶段 3
定时器follow-up 与 schedule 分开存储；scheduler 只把到期项转成事件自动化任务有到点 ticker，Agent 可用 schedule_create 给自己建任务一次性 follow-up 是否已支持，未核对
记忆只存取不回来的信息；指令、笔记、已发消息、任务进度四类；存在持久存储里原生 context 的 checkpoint 存 MySQL，Project 背景每个 Turn 注入，Task 的计划和时间线保存进度容器内文件会随容器丢失，智能体的跨 Run 笔记必须落 MySQL
权限凭证放在 Agent 之外；高风险动作自动审查或延迟调用，等人回复后恢复凭证由 ClawSec 保管，Run 只拿到当前用户的会话；Task 的提问与验收对应「等人回复」自动审查高风险动作的分类器没有
发件箱运行有三种结局：发消息、无需发送、等待输入；从安静开始，用 eval 调消息量回复写成 Task activity，企业微信通知会记录发送状态「判断无需回复」没有显式结局，也没有消息量的评测

上下文开销与压缩

原文提醒，系统提示、工具定义和记忆文件在每次 Run 开头都要加载，所以要保持精简并用 prompt caching。会话过长时压缩或新开会话都会丢细节，重要信息要在过程中写进记忆。Rook 的 Pi 已有压缩和 context 占用估算，但智能体的指令和笔记会增加每个 Turn 的固定开销，阶段 0 要给指令长度设上限。原文的 dreaming（回看过去会话整理记忆）是可选项，本草案不做。

对阶段 1 的影响

文章建议把「直接调用 Agent」改成「写一条事件」。Rook 已有这条路：评论里的 @ 触发写进目标 Session 的 Queue，沿用现有的幂等和暂停规则。阶段 1 因此不需要新的收件箱表。

四个阶段

每个阶段都以一个可验收的用户结果结束，后一阶段只在前一阶段通过后开始。

阶段用户看到什么实现要点
0 智能体定义内置的 Rook，管理员编辑指令和停用，不提供用户创建目录按多个智能体的形状设计，保存在加密配置文档里，不新建表。开放用户创建需要先有每个智能体的连接器和操作白名单。
1 自动回答在需求评论里 @某个智能体，它的回复出现在时间线触发者通过准入后，向该 Task 绑定的 Session 投递一条消息。Run 结束后把回复写成 activity。Task 状态不变。
2 接下游开发Rook 接单、改代码、提交交付，验收人退回或通过Rook 以 agent 身份接单，在会话仓库根里工作，提交 MR 链接作为交付。
3 事件驱动MR 评论、告警、定时事件自动唤醒 TaskDurable Inbox 落表，Worker 领取，Scheduler 写入同一入口。

已定的决定

待决定项已全部确认，其中执行身份、创建权限、个人 skill 和 Task 会话的名字采用默认方案。设计已写入仓库的词表和设计文档。

项决定
触发词智能体自己的名称，写作 @名称。名称全站唯一，允许中文，不含 @ 和空白，可以改名。评论写入时解析成智能体 id 保存，改名不影响已有评论。Chat 里 @superagent 的旧定义失效。
智能体用户创建的、有名称的自动执行者，对应 Grok 的 bot 这类产品里的角色。词表里的「Agent」仍指持有 Task 凭据的外部 Agent。
执行身份触发者。使用触发者的公司 SSO 会话和 Provider，不引入服务账号。
创建权限阶段 0 到 3 只有内置的 Rook，管理员维护。用户创建延后，前提是每个智能体声明可用的连接器和操作白名单，由 Rook Backend 在执行边界强制。
系统 skill对所有智能体可见。可见不等于有权操作，每次 Run 仍按触发者校验，智能体的指令不能提升权限。
个人 skill默认不开放，创建者主动绑定后才可用。
可见范围默认组可见。创建者可以改成仅自己可触发。
Task 会话一个智能体、一个 Task 和一名触发者之间唯一的 Session。不同触发者分开，原生 context 不跨用户共享。
