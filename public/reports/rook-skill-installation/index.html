Rook skill 安装方案

设计方案 · 待实施

摘要

系统 skill 采用和本机一样的目录结构。管理员安装一次，所有 Rook 用户共用。管理员在网页直接更新，下一次 Run 使用新内容。安装记录保存来源和 Git commit。Runtime 从固定目录取得文件。

交付顺序为 PR 1 系统 skill、PR 2 个人 skill。PR 1 从当前基线开始。PR 2 复用 PR 1 的安装操作和 Runtime 加载，并在 PR 1 验收后开始。两个 PR 的界面改动均在合并前审阅。

安装目录和权限

范围 安装目录 谁安装和更新 谁使用
系统 skill 部署账号的 $HOME/.agents/skills/<skillName>/ Rook 管理员 所有获准使用 Rook 的用户
个人 skill <用户工作目录>/.agents/skills/<skillName>/ 该 Rook 用户 Rook 为该用户的 Run 加载
  • 系统来源包含 ai-marketplace、pstack、magpie，管理员可以添加其他来源。目录直接按 skill 名组织。来源配置记录仓库、可选 tag 和已安装的 skill 名。
  • Rook Backend 由部署配置取得系统目录的绝对路径。Runtime 使用自己的执行环境。多个提供服务的 Pod 应读取同一份持久系统目录。Pod 替换后，目录内容继续可用。
  • Rook Backend 在系统安装接口校验管理员身份。Runtime 只有系统目录的读取权限。如果多个 Run 使用同一 Linux 账号，系统目录仍须由受控写入进程或只读挂载保护。
  • 一个 Rook 用户对应一个持久工作目录，路径由 Rook Backend 根据已认证的用户身份确定。工作目录用于安装个人 skill。Runtime 实际执行时的 cwd 继续由当前任务决定。
  • 安装目录与 Linux 执行身份可以分开决定。PR 1 沿用 Rook 当前的数字 UID。PR 2 若采用所有 Run 共用一个 Linux 账号，个人目录只提供加载范围，其他 Run 仍有机会通过文件系统访问。启用这一执行模式前须明确调整项目的用户隔离契约。现有生产契约要求按执行身份隔离。

管理员操作

  1. 管理员在「系统管理 → skill 管理」找到 pstack 或 magpie，点击「更新」。新增来源使用「从 Git 安装」。ai-marketplace 的「更新」放在现有 ClawSec 管理入口。
  2. Rook Backend 使用配置好的 Git 读取授权读取来源。Rook Backend 解析 Git tag 或默认分支，固定本次安装的 commit，并预览新增、替换和移除的 skill。普通更新沿用该来源已选的 skill。已停用项保持停用。同名 skill 归属其他来源时，更新返回冲突。
  3. 管理员确认后，安装器在临时目录准备并校验完整包。Rook Backend 一次提交这个来源的变更。成功后页面直接显示安装结果。失败时保留当前文件和记录。相同安装操作可以安全重试。
  4. 安装记录保留来源、实际 Git commit、操作者、完成时间和内容摘要。页面可以展示实际 commit。运行时以当前安装目录和权限为准。管理界面提供安装、更新、卸载。安装操作完成即生效。

ai-marketplace 继续用仓库自带安装器。Rook Backend 把 skill、ClawSec CLI 和 Pi extension 作为一次安装校验和提交。全新目录可以用镜像内已经验证的包初始化。后续升级由管理员触发，替换 Pod 后继续读取共享目录中的当前安装。

文件切换和 Runtime 加载

  • Rook Backend 把系统来源清单、安装记录和 ai-marketplace 组件放在系统目录内的受控位置。skill 包仍直接位于 <skillName>/。组件和记录随目录一起切换。
  • 实现优先验证在目标共享文件系统上，通过 renameat2(RENAME_EXCHANGE) 一次切换同一文件系统中的候选目录与固定目录。共享存储挂在固定目录的上层，固定目录和候选目录都在挂载内。目录切换前校验来源冲突、文件和组件。在现有 MySQL 的跨实例锁内复核安装记录，再切换目录。读取方在准备 Run 文件时也须取得一致视图。旧目录只作临时清理和故障恢复使用。
  • 一次安装成功即提交。进程中断后，Rook Backend 按固定目录中的安装记录判断是否切换成功，然后清理临时目录。Git commit 和摘要用于核对文件以及识别重复安装。
  • Rook Backend 为每个 Run 提供当前系统 skill 与该用户可用的个人 skill。系统 skill 与个人 skill 同名时沿用系统优先。Runtime 启动前取得完整目录，脚本和附件与 SKILL.md 一起可读。已经启动的 Run 继续读其启动时取得的文件。
Runtime Run 加载入口
Claude Code 把完整包放入本次 Run 的 <workDir>/.claude/skills/<skillName>/，验证托管启动方式能发现它。若当前启动方式禁用了项目发现，使用本次 Run 的 $CLAUDE_CONFIG_DIR/skills/。
Codex 把完整包放入任务专用的 $CODEX_HOME/skills/<skillName>/。
Pi 使用 Run 内的 .pi/skills/<skillName>/，由 Pi SDK 传入明确路径，RPC 使用 --skill。

三个 Runtime 均需验收自然语言使用系统 skill 和显式选择 skill。当前 Claude Code、Codex 只在显式选择时接入 Rook skill，PR 1 补上系统 skill 的默认加载。

PR 1 交付系统 skill 目录和管理员直接更新

  • 从基线核对系统版本记录、个人安装、服务端直接调用系统 skill 的入口和三个 Runtime 的调用方。改动集中在安装器、系统管理 API 和页面、Runtime 加载以及部署和 skill 文档。
  • 在共享目录中迁入当前生效的三个来源及其他已安装系统来源。保留原 commit、已选 skill 和停用状态。按原记录校验内容，重复执行得到同一结果。迁移启动前准备旧实例可读的记录和文件，先让所有写入实例支持新目录，再统一切换写入。保留迁移前记录供部署回退。
  • 从「系统管理 → skill 管理」更新 pstack、magpie，并从现有 ClawSec 管理入口直接更新 ai-marketplace。管理页显示最终结果。普通用户调用更新接口得到拒绝。
  • 验证安装失败、重复提交、进程中断和两名管理员同时更新。检查各 Pod 只看到完整旧包或完整新包。检查 Pod 替换后目录可用。旧 Run 的附件和 ClawSec 组件仍可调用。
  • 使用两个用户账号，在 Pi、Claude Code、Codex 各完成一次旧内容识别和下一次 Run 的新内容识别。普通 Run 与 Pod 重启的 Git 获取次数应为零。用相同的测试 Session 对比变更前后的 Run 准入耗时。
  • 执行 npm run check、npm test、npm run build，更新 SKILL_INSTALLATION.md、CONTEXT.md 和部署说明中的实际契约。

PR 2 交付个人 skill 目录

  • 依赖 PR 1 的安装操作和 Runtime 加载。在用户工作目录建立 .agents/skills/，接入现有个人 skill 页面。核对旧个人安装的归属、当前文件和停用状态，按用户迁入。
  • 用两个账号验证同一用户跨 Session 和跨 Pod 使用个人 skill。检查普通用户无法通过个人安装接口更改系统目录或其他用户的目录。若生产继续要求用户隔离，从另一个执行 UID 实测个人文件不可读。
  • 比较变更前后的 Run 准入耗时。验证只有更新过的来源需要从 Git 获取。运行 npm run check、npm test、npm run build。

本地文件系统已验证 RENAME_EXCHANGE 能交换两个非空目录。生产共享文件系统的持久性、只读挂载和目录交换语义仍需在第一期确认。若目标文件系统不支持该操作，保持旧读取路径，先验证能提供等价切换语义的存储后再迁移。
