Pi 冻结审查

2026-11-27 · 分支 release_fix/session-freeze-20261127，基于 main 3946f37 · 改动未提交 · 范围：src/chat/isolated.ts、src/chat/native.ts、tests/pi-persistent.test.ts、README.md

标注：实测本地 MySQL 和真实 Pi 跑过 推断读代码得出 待做建议的后续改动

结论

可以进入 MR。改动实现了「空闲 30 分钟冻结，本地文件和 MySQL head 一致就直接用本地」。审查没有发现本次改动引入的缺陷。审查找到一个 main 上就有的问题：部分失败的 Run 会把未保存的 Turn 留在本地文件里。本次只修了其中一种失败。冻结会让冷启动变多，所以这个问题在冻结后更容易碰到，建议在同一个 MR 或紧接着的 MR 里补上。

改动做了什么

  • Pi worker 空闲满 IDLE_WORKER_FREEZE_MS（30 分钟）就停止。空闲 worker 的数量上限 ROOK_CHAT_MAX_IDLE_WORKERS 保留。
  • 某个 Session 没有活着的 worker 时，新 worker 先比对本地 native-session.jsonl 和 MySQL head（revision、nativeSessionId、bytes、sha256）。一致就直接用本地文件。不一致时，worker 发 checkpoint_required，Rook 再读 MySQL 全文。
  • Run 以 native_context_persistence_failed 失败时，Rook 以执行用户身份删除本地文件，下一轮从 MySQL 恢复。
  • Claude Code 和 Codex 不受影响。它们不是 persistent 模式，每轮结束就退出进程。

发现

main 已有其他失败也会把未保存的 Turn 留在本地

只有 native_context_persistence_failed 会删除本地文件。native_event_persistence_failed、execution_lease_lost、execution_cleanup_failed 这几种失败不删。冷启动时，readExtendedCheckpoint 会接受前缀和 head 一致、但更长的本地文件，于是把这一轮当成历史接上。界面上这一轮显示失败，模型却能看到它。

推断main 上这条路径就存在：worker 回收后的冷启动会走到它。冻结让冷启动从「数量超限或重启时」变成「每次空闲 30 分钟后」，碰到的概率因此变大。

待做任何失败的 Run 都删除本地文件。只保留一种例外：checkpoint 超过 16 MiB 时会故意不写 MySQL（native_context_too_large），这时本地文件要留着。改之前先补测试：每种失败码各制造一次，确认下一轮的模型请求里没有那一轮。还要核对已绑定、但从没写过 checkpoint 的 Session，删掉本地文件后能否从合成的 header 恢复。

缺测试冻结期间轮换凭据

冻结路径跳过了 credentialHash 比较。新凭据仍会经过 cleanNativeContext 打码：读到一致的本地文件后，clean.recovered 为真，就会改写文件。这一点只读了代码。现有测试只覆盖 worker 还活着时的凭据轮换。

待做在冻结测试段加一轮换凭据的 Turn，断言新凭据不出现在模型请求和 checkpoint 里。

小问题删除失败只记日志

discardLocalContext 调用 setpriv … rm 失败时，只打印 native_context_discard_failed。删除失败时，下一轮冷启动又会接上未保存的那一轮。这种失败的概率低：文件属于执行用户，目录也是 Rook 自己建的。

已排除删除和 worker 退出之间的竞态

保存失败时，Rook 先 stop() worker。finish 只在 child 的 close 事件之后运行，所以 Rook 删除本地文件时 worker 已经退出，不会再写回文件。

已排除多实例下的旧本地文件

Session 被另一台实例接走时，那台机器上没有本地文件，会读 MySQL。之后 Session 回到原实例时，原实例上的旧文件和新 head 的 sha256 不一致，前缀也对不上，于是同样读 MySQL。推断这一点没有用两台真实实例跑过。

中断 Turn 的决定

服务重启时进行中的 Turn，按「断开提示 + t3code 续跑规则」处理：没开始工具就原样重发，最多 3 次；已经开始工具就发续跑提示，要求模型先确认副作用。Orca 的做法是有人确认前不自动重发。它这样做，是因为它的 agent 在应用重启后可能还活着。Rook 的 worker 会随 Backend 一起退出，MySQL 租约过期就能证明这一点，所以采用 t3code 的做法。这部分还没写代码。

没覆盖的

  • 真实的 30 分钟计时器只测了 200 ms 版本。生产环境里冻结后的恢复耗时还没测。
  • 没有发布，没有验收。本地 MySQL 不能替代线上多实例的验证。
  • Claude Code 和 Codex 的冻结属于方案的第 2、3 步，本分支不包含。
