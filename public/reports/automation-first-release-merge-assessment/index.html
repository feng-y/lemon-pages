自动化任务首版合入评估

共用 timer、独立系统 Session、执行详情和错过通知

合入决定

暂缓合入。代码与目标分支存在 Web 冲突，新旧 Backend 混跑会破坏系统 Session 隔离。MySQL 故障演练另外复现了错误的恢复状态。先修复并验证切换与恢复，再审查最终合并内容。

工程与发布

级别问题合入条件
阻塞只读合并检查发现两处 Web 冲突。自动化改动仍在工作区，候选分支已包含另一组产品改动。明确自动化评审范围，单独提交，解决冲突后在合并后的代码上验证。
阻塞新 Backend 启动就写入系统 Session。共享库中的旧 Backend 仍可能按旧目标执行，并把同一所有者的系统 Session 当作普通 Chat 读取和操作。先部署识别系统 Session 与新通知的兼容代码。确认全部共享库实例一致，再开新投递。回滚到同样支持读取和隔离的版本。
发布前修复退出时先等当前 timer 扫描完成，再关闭 Run 受理。待处理任务较多时，扫描可能继续受理 Run，并占用退出时间。先停止受理。让扫描在安全边界退出，并验证下次启动能接手未处理的投递。
发布前修复同一所有者跨任务并发复用请求 ID 时，两个请求可能复用同一个系统 Session，进而使用另一任务的执行配置。先原子确认请求归属，再创建系统 Session。用不同 Project 和 Runtime 验收冲突。

执行语义

级别现象预期
阻塞已受理的 Run 在调用工具前中断。如果恢复时下一轮也已到期，上一轮会从待重排被覆盖为「错过」。本地 MySQL 已复现。区分未投递与已受理后中断。保留上一轮的 Run，并按重排规则处理。下一轮独立推进。
阻塞24 小时的每分钟规则应有 1,440 个时点。带扫描上限的规则只回报 1,000 个，导致少记错过数量。Cron 还可能先运行窗口内的旧时点。等待扫描确定整个窗口的最后一个时点再投递。验收跨上限的 Cron 和 RRULE，验证时间、记录数量和通知一致。
需确认契约立即执行和试跑只有在 Run 受理成功后才写入投递回执。受理前出错没有执行记录。候选试跑详情只保留最新一次。如果首版承诺记录每次手动尝试，需要先写回执，再受理，并按试跑 ID 查询。明确停止、重试与交付物的首版范围。
需确认契约Runtime 已保存部分公开输出但随后抛错时，详情可能显示没有输出。系统 Session 复用 Run 和消息存储。为失败详情保留可展示的输出。确认 Chat 隔离的验收边界是否包含独立消息存储。

验收证据

  • 本地专项通过。构建和浏览器回归通过。包含 Kanban timer、独立 Session、双 Backend 去重和 SSO 夹具的 MySQL 专项测试 53 项通过。
  • 完整测试已结束。349 项通过，161 项跳过，1 项因超时取消。取消项在 Pi HTTP 测试文件单独重跑时通过，该文件共 9 项通过。
  • 故障演练失败。新增的独立恢复复现捕捉到了已受理 Run 被记为错过。长窗口复算也确认了计数上限问题。
  • 环境验收待完成。还需要使用最终合并代码验证真实 Provider、公司 SSO 和企业微信投递。

放行条件

  1. 确定 MR 范围，解决目标分支冲突，并在最终候选上跑构建和完整测试。
  2. 通过共享库的新旧版本切换和回滚测试。用旧的固定目标、未投递记录和已受理记录分别验证。
  3. 通过中断与下一次到期相撞、跨扫描上限、退出排空的故障演练。
  4. 在受控环境验证一次真实投递、一次错过通知及其补跑链接。
