负反馈进入 Kanban 待规划

design synthesis

Rook · 增量通路设计 · 2026-11-25 · 零 DDL · 分支 release_fix/feedback-optimize-20261125

TL;DR

现有链路不变：点踩后反馈照常进入「用户反馈」页。这次在它上面加一条通路，同时创建一条无处理人的 Task，直接进入 Kanban 待规划。

看板项就是 Task，不新增实体。反馈管理员在板上分诊，填处理人、标题、背景、需求类型和业务标签；处理人确认计划后进入待办；无效需求由反馈管理员关闭。用户反馈页保留，等新通路稳定后再移除。

Task 的背景自动来自分享快照的同一段对话，完整快照不复制。待规划期间背景只对反馈管理员、处理人和验收人可见，确认计划后对默认组公开，快照链接始终受限。这次不改表结构。

四个答案

先回答实体、入口、分组和标签，再看流程和边界。

问题结论
看板项是什么 Task（需求）。不新增实体。一条消息反馈最多对应一条 Task，现有唯一键 uk_feedback_request(feedback_id, manual_request_key='') 已经能表达 1:1。
差评怎么进看板 在现有反馈保存链路上加一条通路：保存后同时创建无处理人的 Task。数据库里 status='todo'，创建活动 planning_created，UI 派生为「待规划」。planning 不是新的数据库状态。用户反馈页继续可用。
分组怎么分 默认组不变，仍是全部已准入启用的 RD。看板列表新增「按创建方式」分组：反馈 / 手动。可选筛选 origin=feedback|manual，可保存成「反馈待规划」视图。不新增组成员或路由模型。
标签用哪些 沿用现有两维：需求类型 task_type（feature / bugfix / analysis）和业务标签 business_mask（online / sample / training）。分诊时由人填写，不自动猜。创建方式由 feedback_id 派生。
正文是什么 分享快照的同一段对话生成的摘要：反馈描述 + 提问 + 回答摘要，总长不超过 1000 字。完整快照不复制，Task 只存 share_id 并链接过去。

「分诊」是这次新起的词，指反馈管理员在待规划里填处理人、标题、背景和标签，任务仍留在待规划。拟写入 CONTEXT.md，和现有「移交处理」区分开。

流程

点踩保存是入口，分诊是规划阶段，确认计划才进入待办。

反馈创建的 Task 现有 Task 与动作 虚线 = 过渡期保留 待规划 = 数据库 status='todo' 加创建活动 planning_created

谁在哪一步做什么

  • 用户点踩。saveFeedback 保存反馈并返回反馈 id。这条反馈同时进入用户反馈页和看板，客户端不需要改。
  • 系统创建 Task。chatApi 调 Kanban.ensureFeedbackTask。事务里锁反馈行，创建 Task，写一条 feedback-auto 的 planning_created 活动。Task 没有处理人，created_by=''。
  • 反馈管理员分诊。在需求详情提交 triage，一次写处理人、标题、背景、类型和业务标签。Task 留在待规划，处理人收到一条企业微信。
  • 处理人确认计划。现有 PATCH 把状态改为 todo，服务端清除 planning_created 标记，Task 进入待办。
  • 反馈管理员关闭。无效需求执行 dismiss，Task 置为已完成，保留 planning_created 标记，所以背景不公开。

数据模型与可见性

Task、活动、唯一键和快照全部复用现有结构。新代码只扩展取值和读视图。

不变量

  • 一条反馈一条 Task。唯一键 uk_feedback_request(feedback_id, manual_request_key='') 保证。
  • 待规划是派生状态。status='todo' 且创建活动 activity_kind='planning_created'。
  • 没有处理人不能离开待规划。planning → todo 要求 assignee_id != ''，否则返回 409 kanban_task_unassigned。
  • 不自动回滚。改好评、重复点踩都不删除或完成 Task；无效需求由人关闭。
  • 快照不复制。Task 只存 share_id，正文是同一段对话的摘要。
  • 创建幂等。反馈行 FOR UPDATE 串行化，唯一键兜底，feedback-auto 活动只写一次。

Task 的内容

字段自动创建时分诊后谁可见
title 反馈 #<id>，中性占位 分诊者写的标题 默认组、Agent
description 反馈描述 + 提问 + 回答摘要，≤1000 字 分诊者可编辑 待规划期间：反馈管理员、处理人、验收人；确认计划后：默认组、Agent
shareUrl /share/<share_id>.html 不变 反馈管理员、处理人、验收人
快照 HTML BOSS 密文 不变 持有链接的公司 SSO 加准入用户
feedbackId 反馈 ID 不变 默认组，显示「来源 反馈 #id」
createdBy ''，显示「反馈自动创建」 不变 默认组

读视图必须先拆开两个含义

当前 taskView 把「创建来源」和「背景是否对默认组公开」混在 h.id AS shared_description 里。只把 feedback-auto 加进旧 JOIN，会把受限背景泄露给默认组。设计改成单一两表 JOIN，同时取 h.request_id AS initial_source 和 h.activity_kind AS initial_activity，在 task() 里分别判断。不写子查询，不做三表 JOIN，符合 RDS.md 的读规则。

关键代码形状：创建、读视图和分诊权限

ensureFeedbackTask 的事务顺序。锁反馈行，只处理 dislike；按唯一键复用或插入 Task；只有 created_by='' 且无处理人时才写 feedback-auto 活动；仍在待规划、未指派时才刷新标题、背景和 share_id。旧 handoff Task 走早退，不追加自动活动。

// 1. 锁反馈行
SELECT rating,share_id,detail,handled_at
  FROM rook_chat_feedback_v1 WHERE id=? LIMIT 1 FOR UPDATE
// 2. 唯一键复用或插入
INSERT INTO rook_kanban_task_v1 (...)
  VALUES (?, '', ?, ?, ?, '', '', '', 'todo', 1, ...)
  ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id)
// 3. 只有自动创建的 Task 才写创建活动
INSERT INTO rook_kanban_activity_v1
  (task_id,request_id,activity_kind,author_kind,author_id)
  VALUES (?,'feedback-auto','planning_created','agent','Rook')
// 4. 仍在待规划且未指派时刷新
UPDATE rook_kanban_task_v1
  SET title=?,description=?,share_id=?,revision=revision+1 WHERE id=?

分组与标签

不新建权限组，也不新建标签维度。看板列还是状态，新增的是列表视图。

分组

  • 默认组保持不变。全部已准入启用的 RD。自动 Task 进入默认组。
  • 列表新增「按创建方式」。反馈（feedbackId > 0）/ 手动创建（feedbackId = 0）。来源派生，不落库。
  • 卡片显示「反馈」标记。条件同样是 feedbackId > 0。
  • 保存视图。筛选 origin=feedback|manual 加入 kanban-views.ts 白名单、matchesFilters 和保存视图回放，listGroups 增加分组项。漏掉任何一处，保存的「反馈待规划」视图会静默失效。
  • 不按 Chat 工作区分组。Chat Project 和 Kanban Project 是两套身份，自动映射会暴露工作区名，也会制造空项目。
  • 不新建组成员或路由模型。需要团队路由时，用处理人和现有标签表达。

标签

维度存储取值写入时机
创建方式派生 feedback_id反馈 / 手动创建时确定，不可改
需求类型task_type空 / feature / bugfix / analysis分诊表单
业务标签business_mask空 / online / sample / training，可多选分诊表单
状态status 加活动待规划 / 待办 / 进行中 / 审核中 / 已完成流程

自动创建不猜标签。同一个「回答不对」可能是知识错误、skill 缺失或新需求，自动打标会把错误固化成统计口径。不新增问题分类维度；没有数据源，新增要新列和 RDS 审批。

过渡期两个队列

自动创建不标记 handled_at。反馈仍在用户反馈页的待处理列表，页面显示「已进入看板」和需求链接；每日摘要继续按 handled_at=0 计数；管理员确认后手动标记已处理。新通路稳定、用户反馈页移除后，看板成为唯一队列，再决定 handled_at 和摘要的去留。

旧链路先保留

这次不删 handoff，也不删用户反馈页。反馈页对已有 Task 的差评显示「查看需求」，隐藏「移交处理」，避免旧 handoff 和自动 Task 抢同一条反馈。旧 handoff Task 行照旧显示，不迁移。新通路稳定后再移除用户反馈页，届时再决定 handoff 的去留。

迁移路径

Phase 1 · 本次

在现有反馈链路上增加看板通路。用户反馈页、handoff、现有企业微信通知都不动。反馈页对已有 Task 的差评显示「查看需求」，隐藏「移交处理」。

Phase 2 · 稳定后

移除用户反馈页。看板成为唯一队列；再决定 handoff、handled_at 和每日摘要的去留。移除前保留反馈页，不删除旧数据。

两个默认值

背景什么时候对默认组公开

默认：确认计划后公开。待规划期间只有反馈管理员、处理人和验收人可见。这样默认组在计划确认前只看到中性标题。

要改成分诊时即公开，把 feedback-auto 加进 publicBackgroundSources 一处即可。

旧差评怎么补建

默认：逐条「创建需求」。避免部署时突然生成大量 Task。补建失败或未创建时，用户反馈页保留入口。

要一次性批量补建，需要另定水位、名单和关闭重复的规则。

Open questions 与已接受的取舍

待产品决定。任务完成后同一条回答再次被点踩，是否重开或新建第二条；用户反馈页的待处理是否排除已有 Task 的反馈；是否给反馈管理员批量分诊或按项目路由；每条差评的实时企业微信是否长期保留；同一条回复的 N 条反馈是否在分诊时合并；没有反馈管理员的部署是否给某个默认角色放开分诊；用户反馈页移除后，handled_at 和每日摘要是否保留。

已接受。背景确认计划后才对默认组公开，换取不把未经确认的反馈原文直接摊开；摘要而非快照全文，换取零 DDL 和不复制会话正文；分诊和确认两步，换取「待规划 = 计划未确认」的现有语义；不自动回滚 Task，换取不删除可能已被认领的工作；不自动把反馈标为已处理，过渡期两个队列各自表达状态；不自动补建旧反馈，换取部署时不会灌入历史积压；过渡期保留用户反馈页和 handoff，换取旧入口不中断，新通路稳定后再移除。

已否决。新实体 FeedbackTask；待规划列直接渲染反馈行；自动创建直接进 todo；自动指派给提交人或会话所有者；把快照全文写进 description；按工作区或团队新建组；把问题分类塞进 business_mask。
