Rook SuperAgent 最小闭环

以 dsh-superagent-prototype 为目标，用 Rook agent 处理 Kanban 需求作为验证场景。本页是待确认的设计，闭环部分尚未实现。

TL;DR

MR !179 只做了 super agent 的入口层：智能体定义、管理和评论里 @名称 触发，每次被 @ 就一定回复一条。原型的核心是被接受的工作会订阅它的 Thread，之后的消息不用再 @ 也会送到同一个 Executor，由它决定回复、沉默或请人处理。最小闭环补的就是这一层：订阅、按 Task 串行合批、Runtime 中立的结构化结果，以及每条评论都留下处置记录。闸门仍是确定性代码，@名称 是显式请求，原型对显式请求不跑模型评估，所以不需要在主 Run 之前加一次模型调用。存储沿用 ConfigurationStore 文档，不建新表，不需要 RDS 审批。实现前要先修一个可见范围问题：Run 以 owner 身份执行，但需求描述目前按评论者的权限取出。

原型的闭环

原型的事件只存一次，然后先找订阅它的工作；没人认领才进评估。评估只有接受、停止、忽略、不可用四种结果。回复、沉默和请人处理分散在评估和执行两处。

行为原型里在哪依据
回复评估接受后由 Executor 产出，主 Session 发出prompts/replies.md
沉默评估层是 ignore；已有工作上的普通讨论由 Executor 决定不回admission.md:23，work.md:9
请人处理评估失败记 unavailable；Executor 需要人拍板时发 human_actiondocs/002，handoff-worker.md:1
显式请求只过确定性闸门，不跑模型评估src/app/assessment.ts:39
跟进消息有订阅时直接交给该工作，不进评估src/core/intake.ts:58
并发每个 Thread 同时一个评估，期间到达的消息合成下一批docs/001 Thread 行
不照搬的部分

原型的 Executor 都以运营者的同一个系统用户运行，主 Session 能看到全部 Thread。Rook 有用户隔离，不能设跨用户的常驻主 Session，所以路由由 Rook Backend 的确定性代码完成。原型依赖 DSH 专有的 Session 钩子，Rook 改用最终回复里的约定 JSON，Pi、Claude Code 和 Codex 都能接入。

最小闭环设计

只有一个 Source：Kanban 需求评论。第一次 @名称 被接受后，该智能体订阅这条需求；之后的评论不用再 @，按顺序合批送进同一个 Task 会话，由智能体决定回复、沉默或请人处理。每条评论都留下处置记录。

数据形状

每条需求一份配置文档，替换现在的 agent-mentions。全站一份 agent-pending 只保留「有待处理工作的需求 id」。

type AgentSubscription = {
  agentId: string; runAs: string; sessionId: string;   // Task 会话
  since: number;                                       // 接受它的评论 id
  mandate: { triggeredBy: string; agentRevision: number; strength: 'explicit' };
  ended?: { at: string; reason: 'task_done' | 'dropped' | 'agent_disabled' | 'owner_changed' };
};
type AgentInput = { activityId: number; author: string; kind: 'mention' | 'followup' };
type Disposition = { kind: 'replied' | 'silent' | 'attention' | 'unavailable'; agentId: string; reason?: string };
type TaskAgentInbox = {
  subscriptions: Record<string, AgentSubscription>;   // 按 agentId
  pending: Record<string, AgentInput[]>;              // 按 agentId，Run 进行中时累积
  inFlight: Record<string, { requestId: string; activityIds: number[] }>;
  dispositions: Record<number, Disposition[]>;        // 按评论 id
};
// Run 最终回复末尾的约定 JSON，由 Backend 解析
type AgentResult = { reply: string | null; attention: string | null; report: 'progress' | 'ready' | 'dropped' };

步骤

#步骤现状
1Source：RD 在需求下评论。智能体写的 activity 不进入已有
2去重：评论 activity id 唯一，requestId 由需求和评论 id 确定已有
3闸门：@名称 解析到可触发的智能体则接受；该需求已有未结束订阅则作为跟进；其余忽略，不记录前半已有，跟进是新的
4接受：同一事务写订阅、mandate 和第一条输入新
5合批：同一 Task 会话有 Run 时，新输入留在 pending；Run 结束后把 pending 合成一条 Queue 消息，单批最多 20 条评论新
6执行：以 owner 身份入队 Session Queue，沿用现有单活和幂等已有
7处置：解析结果 JSON；reply 写时间线，null 记沉默，attention 通知处理人和验收人，dropped 结束订阅新，现在每次都写一条回复
8结束：需求完成、智能体停用或删除、owner 变更时结束订阅，之后的评论不再送达新
解析失败时

结果 JSON 缺失或不合法时，由 @名称 触发的批次把整段回复当作 reply 写入，避免丢掉回答；只含跟进的批次记为沉默，原因 unparsed。Run 失败或 owner 的 SSO 会话失效时，@名称 触发的批次写一条「无法运行」并记 unavailable，跟进批次只记处置。

关键决定

以下是我的默认选择。标「待你确认」的三项，你不改就按默认实现。

决定选择理由
收件箱放哪每条需求一份配置文档Session Queue 处在评估之后，上限 20 条，不按需求合批；新表要 RDS 审批，留到接外部事件时
模型评估不做@名称 是显式请求，原型对显式请求只过闸门
沉默由谁决定智能体在结果 JSON 里返回 reply: null对应原型 work.md:9，判断留在 Executor
结构化结果最终回复末尾的约定 JSON不依赖某个 Runtime 的工具注册，三种 Runtime 都能接
跟进消息的权限 待你确认触发者和 owner 的跟进可调整任务；其他人的跟进只作数据原型规定跟进 "grants no new authority"；Run 借用的是 owner 的凭据
请人处理的通道 待你确认先用 Kanban 收件箱通知处理人和验收人已有 views.notify；企业微信通知后加
人工停止 待你确认本轮不做，订阅随需求完成、智能体停用或 dropped 结束原型规定停止只能由人发起，需要一个按钮或命令，不在最小闭环
要先写进 CONTEXT.md 的新词

订阅、跟进、处置、闸门是我新起的名字，实现前加进词表。避开现有词：「准入」已指用户准入，「投递」已指自动化投递，「候选」已指自动化试跑，所以不用这三个词翻译原型的 admission、delivery、candidate。

风险

第一项是现有代码的问题，闭环实现前先修。依据是读代码推断，未实测。

需求描述按评论者的权限取出，却进入 owner 的 Run

Run 的输入里的需求描述按评论者的可见范围投影，Run 却在 owner 的 Session 里执行。反馈来源的需求，评论者能看到、owner 看不到的描述会进入 owner 的原生 context。修法：组装 Run 输入时按 owner 投影，跟进消息同样处理。

订阅扩大了借用凭据的范围

Run 用 owner 的 ClawSec 权限，tools 白名单还没强制。订阅后，组内任何 RD 的评论都会送进 Run。跟进只作数据能降低风险，但不能替代白名单。放开 canCreate 前必须先强制白名单。

全站一份待处理索引是写热点

agent-pending 是全站一份 CAS 文档，上限 500。并发评论会冲突重试。最小闭环规模可接受，接外部事件时改用新表。

验证与推迟

验证场景：内置 Rook 绑定管理员，处理一条来自反馈移交的需求。自动化测试用真实 MySQL 加替身模型；真实模型 Run 需要 Rook 的 SSO 调用方配置和模型 Token，目前仍缺。

#操作通过条件
1RD 评论「@Rook 为什么训练失败」建立订阅；Rook 回复一条；处置为 replied
2同一 RD 不带 @ 追问「日志在哪」送进同一 Task 会话；Rook 回复
3Rook 的 Run 进行中，另两人各评论一条合成一批，只起一次 Run
4另一 RD 评论「收到，谢谢」Rook 不回复；处置为 silent，界面可见「已读未回复」
5Rook 判断需要验收人决定处理人和验收人收到通知；处置为 attention
6需求标为完成后再评论不再送达，无新 Run
7owner 看不到原反馈描述的需求上触发Run 输入里没有该描述
