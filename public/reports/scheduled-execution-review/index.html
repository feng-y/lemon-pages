评审结论执行边界状态机可靠性执行结果验收

独立自动化执行 · 设计评审

定时投递、状态机、故障恢复与执行结果

评审结论

每次定时到期、立即执行和试跑都拥有独立的 Runtime Session。共用 timer 和 Scheduler，执行器直接消费持久投递，结果在自动化任务里查看。「不漏执行」要求每个有效到期都有可追踪的处置记录。对外部动作结果不明的投递，保留证据并进入待核对。

一、执行边界

任务定义负责指令、计划、创建者身份和运行配置。创建只保存定义。共用 Scheduler 处理定时到期，立即执行和试跑直接创建投递记录，三者进入同一执行器。执行器直接调用 Runtime，独立于对话发送、对话队列和对话历史。工作区与 Runtime 可以共用，原生 context 按投递隔离。

谁触发、怎么执行、怎么记录

触发 · Scheduler

共用 Scheduler 扫持久 timer。到期后，在同一事务里保存投递和指令快照，再推进游标。立即执行和试跑由用户动作直接写入投递。

执行 · 自动化执行器

执行器按投递 ID 领取租约，重验创建者身份和权限，再直接调用 Runtime。每次投递创建自己的 Runtime Session。

记录 · 自动化任务

执行器追加工具、trace、输出和错误，保存 Runtime 终态与交付物引用。用户按单次投递查看结果，HTML 可预览或下载。

和现有 DSH 方案怎么协同

继续使用 DSH 的时间库计算 RRULE、时区和下次到期，沿用创建只保存定义、以及 new 每次投递独立 Session 的语义。任务页和 schedule_create 等工具走同一套自动化任务接口，共用任务版本和权限校验。到期时由共用 Scheduler 持久化投递并触发执行器。执行结果与 DSH 的回执一样按次可追踪，并补上 Runtime 终态、执行过程和交付物。

迁移期间，已受理的旧投递走原路径结算。旧任务定义和历史回执仍可读。切换到期归属后，共用 Scheduler 成为唯一到期写入方，使用同一个到期去重键。旧的复用目标从切换点开始转为每次新建 Session。

参考实现采用的做法
DSH沿用定时规则、创建与执行分离，以及 new 每次新建 Session 的语义。借鉴投递回执与追加 Session 日志分别保存的做法。DSH 自带 timer 和会话收件箱，整套接入会引入另一套调度入口。
t3code借鉴 new_thread 和确定性启动请求。调度受理与 Runtime 终态分别记录。
Orca单次 Run 详情可直接查看状态、结果、错误和可用用量。信息结构可供参考。
Codex App Server借鉴持久原生标识和 Turn 事件。新投递新建 Thread；同次投递能否恢复由 Runtime 的确认能力决定。

二、完整状态机

任务定义。 启用的任务拥有下一到期点。暂停阻止新投递，也阻止尚未进入启动边界的定时投递。恢复时，从保存的计划游标按策略处理停顿区间。删除采用软删除，保留执行历史和终态。只有规则无后续时点时结束。已进入启动边界的执行沿用快照，需显式停止。编辑以版本和生效时间界定新旧规则，审计记录版本切换。

投递状态进入条件与下一步
pending 待领取到期或手动请求写入投递，冻结指令及资源引用。并发领取用条件更新转到 leased。启动前取消可记为 stopped，计划被暂停、删除或显式替代时记为 skipped。
leased 已领取保存执行者、租约期限和单调递增的代次。重验创建者身份、权限、Provider 及资源。临时错误进入 retry_wait，确定拒绝进入 failed。通过后先提交启动意图，再调用 Runtime。
starting 正在启动保存启动幂等键和独立 Session 关联。Runtime 确认开始进入 running。明确未受理才可安全重试；受理结果未知时查原生记录，无法确认则进入 needs_review。
running 执行中续租并追加执行事件。收到 Runtime 终态后写入可恢复的终态证据，进入 finalizing。执行者失联则优先按原生标识查询、续接或隔离；无法判定结果且可能已执行时进入 needs_review。
finalizing 保存结果以确定性键提交输出、错误和交付物清单。短暂存储错误只重试保存。提交成功、确认失败或确认取消后写对应终态。必需的交付物缺失时，记录失败阶段为结果保存，保留 Runtime 的实际终态。
retry_wait 等待重试保存错误、尝试次数和下次可领取时间。仅重试尚未启动或 Runtime 明确保证可安全重放的投递。租约换代，投递 ID 保持稳定。达到预算后标为失败。
stopping 正在停止记录停止意图，向原生执行发出取消。Runtime 确认取消才记为 stopped。如果正常终态先确认，按实际结果保存。无法确认时进入 needs_review。
needs_review 待核对保存已有结果、trace 和可能的外部动作。可补查终态后进入结果保存。永久未知时由授权用户记录处置后关闭。重新运行是一次明确的新投递。
终态succeeded、failed、stopped、skipped、missed。终态对重复消息幂等。失败和停止保留已产生的可见输出。missed 明确表示计划时点按策略未执行。

三、如何保证到期不丢

崩溃窗口保存与恢复约定
扫描到期后，事务提交前退出在同一事务内写入投递或错过记录、任务版本及指令快照，再推进持久游标。任何一步失败，整笔回滚。时间统一用实际计划时点而非扫描时钟。
事务已提交，唤醒丢失投递记录本身就是可领取的持久工作。启动和周期扫描会补领。唤醒只缩短等待。多个 Scheduler 用计划 ID 与到期时点的唯一键去重。立即执行和试跑用带任务范围的请求 ID 去重。
停机跨过多个到期点建议严格任务逐次补跑，按计划顺序分批入队并限制处理速度。允许合并的任务可以显式选择「只补最近一次」，其余写入 missed 记录或区间并保存首尾时点、数量和规则版本。默认策略在迁移时要明确，背压期间不覆盖已受理投递。
领取后实例退出或恢复过慢租约到期后按阶段回收。领取和状态写入使用代次校验，旧实例不能覆盖新状态。分页扫描待领取、待恢复及待保存记录，避免旧长任务堵住后面的完成记录。
已调用 Runtime，启动回执未写入先持久化启动意图与幂等键。只有 Runtime 确认未受理，或提供可靠去重时，才允许重新发送。外部写工具需独立幂等键或后置核对。无法确认时保留待核对状态。
Runtime 已结束，交付物尚未完成先持久化原生终态与输出引用，按相同对象键重试保存并校验完整性。最后提交用户可见的结果和终态。清理未引用对象需有保留窗口，避免与保存重试竞争。

保证边界。 本地唯一键和原子事务可以保证有效到期被记录一次。实际执行完成依赖存储恢复、可用 Runtime、有效权限和明确的补跑策略。通用系统无法凭本地租约断定外部写入是否已发生。用户需要逐次执行时，应在启用任务时明确选择补跑策略。

四、保存与展示

数据保存内容查看方式
投递与执行摘要投递 ID、任务版本、计划与实际时间、触发方式、尝试次数、Runtime、状态、失败阶段、错误码及可用 trace ID。执行列表与单次详情的页头。
追加事件以投递 ID、尝试代次和事件序号去重。记录领取、鉴权结果、启动、工具开始和结束、耗时、重试、取消和终态。只展示 Runtime 确实上报的事实。展开执行过程，支持分页和按序续读。工具参数、输出和错误只保留有界、脱敏预览。
文本与 HTML 交付物保留最终文本、失败时的已生成输出，以及每份报告的对象引用、格式和完整性信息。每份报告只关联这次投递。详情直接读文本、预览或下载 HTML。授权使用任务权限，HTML 在隔离环境中预览。

执行结果、工具事件和交付物都可以用投递 ID 追溯。报告可以是 HTML，执行事件继续使用结构化记录。保留期内详情允许授权用户复核，凭据和原生私有 context 不作为用户可见输出。

五、评审结果与验收

三轮评审。 第一轮核对现行执行边界，确认默认 Session 复用和 Chat 投递都要替换。第二轮逐步检查故障窗口，确认先推进游标会漏执行，结果不明仍重试可能产生重复外部动作。第三轮核对用户可见结果，要求独立保留事件与报告、区分受理和执行终态，并用分页避免较早的长执行挡住其他结果。

评审项验收标准
任务语义与权限创建不启动 Runtime。连续两次到期、立即执行和试跑生成独立 Session。原生 context 不串用。使用创建者权限，撤销后任务不能启动。Kanban 同一任务的 timer 仍续接它自己的 Task 会话。
掉电、重复和积压在提交前后、启动前后、结果保存前后逐处故障注入。双实例扫同一时点只有一条有效投递。漏唤醒可补领，停机时段逐条或按区间可对账。大量长期执行不会饿死终态保存。
停止和副作用分别测试排队停止、启动中停止、正常结束与停止并发、旧租约写回、工具已开始后失联。停止结果遵循 Runtime 证据。副作用结果不明时无自动重放。
输出与隔离两次报告可独立预览下载。失败保留部分输出。工具事件和用量符合真实 Runtime 能力。不同用户无法访问对方的 trace、产物或结果。
迁移和上线先按部署批次启用读取和新执行入口，再切换到期归属。旧路径已受理的投递沿原路径结算，未受理的投递按切换点只进入一边。验证历史仍可读、旧实例不会重复领取。
模型检查范围

TLC 在两个到期时点模型中遍历 3,307 个状态。到期记录、成功结果、启动后禁止无条件重放、工具执行前置条件、跳过状态及无死锁检查均通过。单次投递视图遍历 58 个状态。故意去掉投递写入，只推进游标后，TLC 在一步内发现到期丢失。

状态模型覆盖两个到期时点、两代租约、启动中失联、停止和结果保存。它将存储提交抽象为原子动作，省略实际 SQL、时区边界、手动入口、权限撤销、文件存储、真实 Runtime 和补跑时钟。结论只适用于所检查的状态空间，落地后按上表做故障注入。
