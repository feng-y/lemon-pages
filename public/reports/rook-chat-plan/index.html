Rook Chat 方案

方案，未实现

让用户用 Rook 和用 dsh 一样，支持 Pi、Claude Code、Codex 三种 Runtime。依据 dsh 源码、三种 Runtime 的实测和业界做法。

TL;DR

dsh 怎么做，Rook 就怎么做。只为两类差异做适配：多个 agent runtime，以及多用户（公司认证与 Session 隔离）。不破坏用户隔离的地方都复用 dsh。

每个 Session 一个常驻进程，和 Claude Code、Codex 在终端里的形态相同。不限制活跃 Session，容量靠扩容。不活跃的 Session 冻结，有新消息时恢复。实例退出和冻结后恢复走同一个机制。

恢复照 dsh 的 resume：关闭被中断的 Turn，不自动继续。过长的对话靠压缩：Pi 由 Rook 照 dsh 实现，Claude Code 和 Codex 用原生压缩。

术语

「常驻进程」是本方案新起的叫法，指一个 Session 在一个执行实例上的长期 Runtime 进程。「压缩」指 Runtime 在同一原生会话内用摘要替换旧历史。会话交互按 Session、Turn、Step 三层。文中标注「实测」的来自源码或运行结果，「推断」的还没有验证。

Session 与常驻进程

一个 Session 由一个进程承载，Turn 写进同一个进程。

dshRook偏离原因
执行单元Web host：一个进程装多个 Session（实测）。终端：一个 Session 一个进程每个 Session 一个常驻进程，在执行实例上照终端形态。Claude Code、Codex 原生就是一个 Session 一个进程，Rook 不改它们。uid 只要求不同用户不共用进程，不决定进程个数
Turn写进同一个 agent写进同一个常驻进程无
写入方每个 Session 一个写入方Session 记录上的执行实例（已有）多实例部署，写入锁要跨机器，放在 MySQL
回收不回收不活跃就冻结，有新消息就恢复进程在服务端，不在用户终端。容量靠扩容
  • 不限制活跃 Session。不做内存预算，不做 LRU，不按个数回收。
  • 冻结。Session 超过 T 分钟没有 Turn，就停掉常驻进程。T 待定，建议 30。
  • 实例退出就是冻结。发布、缩容、崩溃和冻结后恢复走同一个机制，不单独设计交接。

持久化

dsh 的 Session 是仅追加的事件日志，按事件写，200 ms 批量；模型请求前、顶层工具执行前、下一个 Step 前强制 flush（实测）。

Rook 存的层用途现状
RunEvent 日志页面显示与 followPi 已有。Claude Code、Codex 不转发实时事件，要补
原生 contextRuntime 恢复用的会话文件已按仅追加的分块存进 MySQL
  • 为什么是两层。Claude Code 和 Codex 的模型历史在它们自己的会话文件里，Rook 不能从事件日志派生。
  • 检查点照 dsh 的屏障。工具开始前、每个 Step 结束时，把原生文件的增量追加进 MySQL。三种 Runtime 的原生文件都只追加（实测）。Pi 用 Step 和工具开始事件，Claude Code 用 stream-json 的 tool_use、tool_result，Codex 用 item/started、item/completed。
  • 去掉 16 MiB 原生 context 上限。dsh 不限制存储大小。原生文件压缩后不变小（实测）。Pi 超过上限后 Rook 不再提交检查点，恢复时会丢历史（实测）。

恢复

照 dsh 的 resumeWith（实测）。恢复只补齐中断的 Turn，不替用户继续。

  1. 用户操作这个 Session 时才恢复。启动时不批量恢复。
  2. 拿写入权，从检查点写回原生文件。HOME 和路径规则不变。
  3. 关闭被中断的 Turn。已开始、无结果的工具记「结果未知」，只读或幂等才重试，有副作用先核实或问用户。未开始的工具记「未开始」。再补 step/end 和 turn/end {reason: interrupted}。
  4. 不自动继续，等用户发下一条。

过长的对话：压缩

dsh 没有跨会话交接，只有压缩（实测）。Rook 照搬它的做法。

dsh 的环节做法
触发每个 Step 发请求前检查。阈值 min(0.8W, W−O−65536)，W 是窗口，O 是输出上限。Step 之间同步压缩，Turn 不中断
先剪工具结果超过 8192 字符的只留前 4096 和后 1024。剪完低于阈值就不做摘要
再做摘要同一个模型，8 个固定小节。最近 (W−O)×0.16 逐字保留。摘要前导语要求直接继续、不提压缩
超限补救模型返回上下文超限时，最大缩减后重试同一请求，最多 1 次
失败记 warn，用原历史继续
页面日志只追加，页面保留完整历史，压缩处显示一行「上下文已压缩」
Runtime做法
PiRook 照 dsh 实现，删掉现有的上下文预算拦截。它在 Pi 的阈值之前就拒绝发送：1M 窗口时 Rook 在 782,609 token 拒绝，Pi 到 983,616 才压缩（实测）。线上 Session 反复报上下文预算错误，原因很可能在这里（推断）
Claude Code原生压缩，不改参数。默认开启，Rook 没有关（实测）。页面显示 compact_boundary
Codex原生压缩，不改参数。默认开启（实测）。页面显示 contextCompaction

多用户适配

这是 Rook 相对 dsh 的第二类差异。现有的隔离做法都保留。

项做法原因
运行身份每个用户一个数字 uid（100000 + 用户记录 id），用 setpriv 切换，不创建 Linux 用户（现有，实测）用户隔离
HOME每个 uid 一个目录，权限 0700，同一用户的 Session 共用（现有，不改）用户隔离
工作目录每个用户一个，属主为该 uid（现有）用户隔离
公司认证凭据Turn 开始时比对凭据摘要。变了就按「恢复」一节重启常驻进程，再执行这个 Turn凭据在进程环境里，运行中的进程换不了
skillRuntime 启动时传一个 skill 目录，目录对用户只读系统 skill 目录另行检查，不在本方案

发布

  • 收到 SIGTERM。不再接新 Turn（已有）。空闲的常驻进程立即冻结。正在跑的 Turn 等到平台宽限结束。
  • 宽限内没跑完的 Turn。下次用到时按「恢复」一节处理。
  • 删掉 SIGTERM 后 5 秒取消 Run。
  • 宽限时间待定。现在是 60 秒，一个 Turn 最长 1 小时。
要删掉的

Claude Code、Codex 的单次执行；按空闲进程个数回收；Pi 的上下文预算拦截；16 MiB 原生 context 上限；SIGTERM 后 5 秒取消。

顺序与验收

每一步单独验收，三种 Runtime 分别记录结果。

步内容验收
0探测，不改产品代码：Claude Code 一个进程跑多个 Turn 和 Turn 中追加；Codex 同一 thread 连续 turn/start 和 steer；三种 Runtime 写入中断补齐后换实例能否 resume结果写进 Runtime 契约文档

4发布等待发布期间有 Turn 在跑，Turn 正常结束或下次恢复为已中断，不出现 5 秒取消
