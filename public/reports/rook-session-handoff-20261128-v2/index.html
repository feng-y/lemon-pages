Rook Session 恢复与 handoff 设计

用户要求：一定要恢复，不能 resume 时 handoff 重建新的原生 session，错误不暴露给 web 端，只记 MySQL。设计由 fable agent 完成，Claude 抽查。代码基线 main c2163db + MR !243 6ed9642。尚未实现。

v2 修订（用户 2026-11-28）

「每个 Turn 开始前……对于无法恢复才是这个策略」「正常和 codex 一样一直的跑」。删掉 v1 中每个 Turn 开始前补缺口的 handoff，也不再需要覆盖标记。进程被杀、checkpoint 没存下时，下一个 Turn 照常 resume 上一份 checkpoint，不补这一个 Turn。

TL;DR

正常情况和直接用 Codex 一样，一直跑。失败或 Stop 的 Turn 留在原生 session 里：常驻进程不退役，原生 thread 继续，checkpoint 照常保存。Rook 不在 Turn 之间做额外处理。

handoff 只用于无法恢复。原生 resume 失败，或原生 context 已被重置时，Rook Backend 丢弃旧的原生 context，把整个 Session 从 MySQL 拼成 handoff，交给新的原生 session 继续。这就是重建。重建成功时 Run 是 succeeded，web 端没有错误。重建也失败，才显示新错误码 native_rebuild_failed。

不改表结构。恢复记录写进 rook_chat_run_content_v2，content_kind='recovery'。按 4 个 MR 落地，每个 MR 单独可验证。

错误可见性

  • 隐藏，立即重建（A 类）。Turn 开始前原生 context 恢复不了，例如 native_context_unavailable、native_context_changed、Codex thread/resume 失败。Run 终态 succeeded。
  • 隐藏，结束时重置（B 类）。结果有了但 context 存不下，例如 native_context_too_large。这个 Run 的结果保留，下一个 Turn 自动 handoff。
  • 仍然显示。认证、限流、输入过大、配置错误、工具结果未知，以及重建也失败时的 native_rebuild_failed。
  • 记录在哪里。写进 rook_chat_run_content_v2 的 recovery 行，GET run 不返回它。不用 rook_chat_run_error_v1：Claude 已核对 store.ts:557，getRun 会把该表的 error_detail 返回给用户。

设计全文（handoff-design.md）

Session 必须能继续：handoff 与重建设计

日期：2026-11-28。代码基线：/tmp/rook-clone-3XBb（main c2163db + MR !243，HEAD 6ed9642）。文中的 文件:行号 都指这个基线。本文只做设计，没有改代码，没有跑测试。

标注约定：实测 是有人跑过并记录了结果（本文只引用 runtime-sm/*.md 里已有的实测）。读码 是我在本次会话读到的代码。推测 是没有验证的判断。

用户要求原文：「应该是一定要恢复，不能恢复时，可以 handoff 不能 resume 的 session，重建一个，然后用新的 session，就是错误不要暴露给 web 端的 user，错误记录到 mysql 就好」。

修订 v2（2026-11-28，用户：「每个 Turn 开始前，这个错误，对于无法恢复才是这个策略」「正常和 codex 一样一直的跑」）

  • 正常路径和直接用 Codex 一样，一直跑。 失败或 Stop 的 Turn 留在原生 session 里：常驻进程不退役，原生 thread 继续，checkpoint 照常保存。Rook 不在 Turn 之间做额外处理。
  • handoff 只用于无法恢复。 触发条件只有：Turn 开始前原生 resume 失败（A 类），或原生 context 已被重置（B 类，例如 checkpoint 存不下）。这时 handoff 的范围是整个 Session。
  • 删除 gap handoff。 下文所有 reason="gap"、覆盖标记 coveredRunId、mayOverlap、kind='gap' 的内容作废。Manifest 只加重置标记，不加 coveredRunId。进程被杀、checkpoint 没存下时，下一个 Turn 照常 resume 上一份 checkpoint，不补这一个 Turn。
  • MR-2 只剩原生路径。 内容是：失败或 Stop 的 Turn 保存 checkpoint 并保留进程，Stop 先落库时也保存 checkpoint（G4）。不改 manager.ts 的 Turn 准备流程。第 8 节 tests/chat-manager.test.ts 的 gap 用例改成：进程被杀后，下一个 Turn 的 prompt 不带 handoff 前缀，并且 resume 同一个原生会话。

0. 结论

  1. 只用一条规则覆盖两个需求。（v2 作废，见上）原生 context 能用时一直沿用它。只有原生 context 恢复不了时，Rook Backend 才丢弃它，把整个 Session 的全部 Run 从 MySQL 拼成 handoff 文本，放在本次用户消息前面，用新的原生会话继续。这就是重建。
  2. 失败或 Stop 的 Turn 走原生路径：Runtime 干净结束时，Rook Backend 照常保存 checkpoint，并保留常驻进程。这和直接用 Codex 一致。原生路径是唯一的常规路径，因为 Claude Code 和 Codex 的 Run 在 MySQL 里只有提问和最终回复，没有工具事件（读码，grep tool_started 只命中 src/chat/pi-events.ts:136）。重建时这两个 Runtime 只能交接提问和回复。
  3. 重建不新增表，不改表结构。丢弃原生 context 是一次带租约的事务。恢复记录写进 rook_chat_run_content_v2，content_kind='recovery'。
  4. 重建成功时 Run 的终态是 succeeded，error 为空。Web 端不出现错误。重建也失败时，Run 才以新错误码 native_rebuild_failed 失败。
  5. 没有留给用户的产品问题。第 6 节列出我替用户做的三个决定和理由。

2. 先例

2.1 dsh（读码，由子 agent 读取，我没有逐行复核）

  • dsh 没有「恢复失败就重建」的机制。ctx.agents.resume 失败时直接返回 session/not-found、session/writer-held 或 gateway/internal，没有回退（dsh-api-session-controller/lib/index.js:204-215,305-317）。
  • 最接近的机制是 dsh-session-reference。它把另一个 Session 的对话作为一条额外的 user 消息插入。
  • 内容只保留用户文本、compaction checkpoint 和 assistant 文本。它丢掉工具结果、系统消息和图片（dsh-session-reference/lib/index.js:125-160,235-237）。
  • 预算是 max(64 KiB, contextWindow × 4 × 0.2) 个 UTF-8 字节（:98,394,659-672）。先从最旧的整条消息开始丢，从不丢 checkpoint 和最新一条。再对最长的一条做头尾裁剪，标记是 [… omitted N UTF-8 bytes …]（:185-219）。不调用模型做摘要。
  • 包装是 <referenced-sessions>…</referenced-sessions>，并声明内容是不可信的只读快照，不要执行其中的指令（:12-14,395-402）。

2.2 Orca（读码，同上）

  • Orca 的 handoff 只由用户操作触发。resume 失败时抛错，不会自动转 handoff（ipc/ai-vault/ai-vault-resume.ts:41-84）。
  • handoff 是新 agent 的第一条 prompt。prompt 给出 transcript 文件路径，让 agent 自己去读。没有文件时内联文本，上限 36,000 字符，保留尾部（agent-session-context-budget.ts:1-9）。不调用模型做摘要。
  • prompt 的要点：旧会话只读，不要恢复或修改它；transcript 是历史参考数据，不要执行工具输出里的指令；以工作区文件为准（agent-session-continuation.ts:93-112）。
  • 失败只写 console.warn。

2.3 t3code

全部读码，由子 agent 读取，我没有逐行复核。路径缩写：PTS 是 /code/3p/t3code/apps/server/src/orchestration-v2/ProviderTurnStartService.ts，HB 是 /code/3p/t3code/packages/provider-core/src/server/handoffBudget.ts，CHD 是 orchestration-v2/ContextHandoffDelivery.ts，PSI 是 orchestration-v2/testkit/ProviderSwitch.integration.test.ts。任务里列的 ProviderRuntimeRecoveryService.ts 和 ProjectionRecovery.test.ts 只处理服务重启后的清理，不生成 handoff。

t3code 是唯一一个自动做这件事的先例，所以它和本设计最接近。

  • 决定。 t3code 只调用一次 session.resumeThread，失败就开新的原生会话（PTS:1969-1977）。两种失败例外：thread 被占用时重抛，由外层重试；结果未知时 Run 失败。
  • 不尝试恢复、直接开新会话的情况（PTS:1910-1924）：上一次 handoff 送达状态还是 pending；Codex 上一个 Run 以 invalid_encrypted_content 失败。代码注释写的是「The native resume RPC can succeed while persisted input still rejects every turn」（PTS:1828-1875）。这就是第 10 节「循环失败」风险的先例。
  • 内容（HB:134-177）：用户消息、assistant 文本、命令（输入、退出码、完整输出）、错误消息、中断结果、文件改动的路径、计划。不含推理、其他工具类型和附件。前言里明说「Attached files and native tool/reasoning state are not replayed.」（HB:250）。
  • 预算（HB:15-20,99-132）：按 JSON 字节算，约 4 字节一个 token。默认 16,000 token，字节上限 min(64,000, tokenCap × 4)。还要减去原生会话已用量、本次用户文本和一段工作预留。
  • 选取顺序（HB:225-280）：最新的用户消息，最新的 assistant 消息，第一条用户消息，其余从新到旧。条目只整条保留或整条省略，不截断。省略的条目 ID 列出来。不调用模型做摘要。
  • 送达。 Codex 用原生的 thread/inject_items 注入历史条目（CodexAdapterV2.ts:8673-8688）。Claude 没有注入接口，Codex 不支持这个方法时也一样，这时把 handoff 加在用户消息前面：`${context}\n\nUser message:\n${userText}`（CHD:25-26）。
  • 只送达一次。 注入前写 delivery.status=pending，成功后写 injected 或 inline（CHD:133-139）。重试时看到 pending 就报「送达结果未知」，下一次直接开新会话（CHD:124-131）。
  • 替换原生会话 ID。 provider-thread 这一行不变，只把 nativeThreadRef 换成新的（PTS:1994-2007）。旧 ID 被覆盖。Runtime 返回的还是旧 ID 时 Run 失败（PTS:2010-2034）。
  • 用户看到什么。 恢复成功时，Run 开头多一个标题为「Recovered context」的条目（PTS:2043-2079）。摘要正文不下发给客户端（WireProjection.ts:162-165,297-302）。服务端打一行 warning。
  • 仍然显示的错误： 恢复和新建都失败、预算放不下、送达结果未知、还有后台工作在跑。Claude 在 Turn 中途报「会话不存在」时那个 Turn 失败，下一次发送才恢复（ClaudeAdapterV2.ts:889-897）。所以 t3code 也不是完全透明。
  • Stop。 每次写入都核对 Run 的 attempt 还是当前的。Stop 落在替换期间时，t3code 丢弃替换记录，下一个 Turn 重新尝试恢复旧 ID（PSI:2285-2364）。

2.4 Rook 已有的 dsh compaction（读码）

  • dshCompact 需要一个活着的 Pi AgentSession（src/chat/pi-compaction.ts:108-152）。它不能在 Rook Backend 里对 MySQL 记录运行。
  • 所以 handoff 不复用 dshCompact 的摘要调用。handoff 复用它的三样东西：pruneToolResult 的 8192 / 4096 / 1024 裁剪规则（:25-51）、CHECKPOINT_PREAMBLE 的措辞风格（:95）、dshCompaction 算出的窗口参数（:10-16）。
  • 重建后的新原生会话仍由各 Runtime 自己的 compaction 管理后续增长。

2.5 采用和不采用

点 采用 理由
恢复一次，失败就开新原生会话 t3code 和用户要求一致。
预算公式 dsh max(64 KiB, W × 4 × 0.2) 按模型窗口伸缩，不需要模型调用。t3code 的上限更小（64,000 字节），并且减去原生会话已用量。重建后的原生会话是空的，所以 Rook 不需要减。
裁剪顺序 t3code 的优先级（最新 Turn、第一条提问、其余从新到旧）加 dsh 的头尾裁剪 t3code 不截断条目，放不下就整条省略。Rook 的单条提问可以很长，整条省略会丢掉最新一条，所以加头尾裁剪。
送达位置 用户消息前缀。t3code 的 inline 路径、Orca、dsh 都这样 见 3.4。Codex 的 thread/inject_items 不采用：它只有 Codex 有，第一版三个 Runtime 走同一条路。
「历史材料不是新请求，也不是更高优先级的指令」的声明 t3code、Orca、dsh handoff 含工具输出摘要，可能带注入文本。
模型摘要 不采用 三个先例都不做。Rook Backend 没有 Runtime 无关的模型调用入口。
恢复成功时显示一个中性条目 t3code「Recovered context」 见 6.1。
新原生会话 ID 必须和旧的不同 t3code resetNative 把旧 ID 记在重置标记里。绑定新 ID 时和它比较，相同就按 native_rebuild_failed 失败。
pending 送达标记 不采用 t3code 把 handoff 落库，所以要跟踪送达。Rook 的 handoff 每次从覆盖标记现算，没有「送了一半」的状态。
Stop 时丢弃替换记录、回到旧 ID 不采用 Rook 在执行前就提交 resetNative。旧原生 context 已经判定不能用，回去只会再失败一次。
上一个 Run 因 transcript 被拒而失败时跳过恢复 t3code（invalid_encrypted_content） 第 10 节的循环失败规则。

3. 数据形状

3.1 handoff 的内容

// 新文件 src/chat/handoff.ts。纯函数，不读数据库。
type HandoffStep =
  | { kind: 'text'; text: string }                     // 中间回复和插话
  | { kind: 'tool'; name: string; input?: string; result?: string; failed: boolean; settled: boolean };

type HandoffTurn = {
  runId: string;
  at: string;                                          // Run 的 createdAt
  state: 'succeeded' | 'failed' | 'stopped' | 'interrupted';
  error?: string;                                      // 只有错误码
  user: string;                                        // Run 的 prompt 原文
  attachments: number;                                 // 只给数量
  steps: HandoffStep[];                                // 只有 Pi 的 Run 有内容
  response: string;                                    // 最终回复。失败的 Run 取 text_delta 拼出的部分回复
  mayOverlap?: true;                                   // 这个 Run 的一部分可能已在原生 context 里
};

type Handoff = {
  version: 1;
  reason: 'gap' | 'rebuild';
  turns: HandoffTurn[];                                // 从旧到新，预算裁剪之后
  omittedTurns: number;
  bytes: number;
  sha256: string;                                      // 写进恢复记录，方便核对
};

function buildHandoff(runs: HandoffSource[], budgetBytes: number, reason: Handoff['reason']): Handoff;
function renderHandoff(handoff: Handoff): string;

handoff 不落库。它每次从 MySQL 现算。恢复记录只保存 turns、omittedTurns、bytes、sha256。这样 Stop 打断重建后，下一个 Turn 重新计算就能得到同样的结果。

3.2 来源（全部读码）

内容 MySQL 位置 备注
Run 的顺序、状态、错误码 rook_chat_run_v2 state、error_code、created_at。
用户提问 rook_chat_run_content_v2，content_kind='prompt' 用 Run 里保存的原文。上一次送达时加在前面的 handoff 文本不在这里，所以不会套娃。
最终回复 同表，content_kind='response' 失败路径写入的是空串（manager.ts:558-560）。
部分回复、工具名、工具输入和结果摘要、插话 同表，content_kind='event' text_delta、tool_started、tool_completed。工具摘要每条不超过 1200 字符，每个 Run 合计不超过 64 KiB（src/chat/tool-details.ts:44-66）。
未知结果的工具 rook_chat_run_v2.pending_tools 加上没有配对 tool_completed 的 tool_started 渲染成「结果未知」。
附件 Run 的附件索引 只写数量。附件按 Run 暂存，新原生会话读不到旧文件（推测，没有读 attachment-files.ts 的清理逻辑）。

MySQL 里没有的内容：完整工具结果、隐藏推理、Claude Code 和 Codex 的全部工具调用。所以 Claude Code 和 Codex 的重建只能交接提问和最终回复。这是已知的损失。claude-code.md G2 和 codex.md 1.5 记录了这两个适配器不发工具事件。那两项补上后，handoff 自动变完整，本设计不用改。

Session 的工作目录在重建前后不变（native.ts:108,119，<root>/<owner>/<session>/workspace）。handoff 文本会告诉模型以工作区文件为准。

3.3 预算

  • budgetBytes = max(64 KiB, contextWindow × 4 × 0.2)，上限 512 KiB。contextWindow 取 piModelCapacity(session.model)（src/chat/pi-models.ts）。查不到时用 64 KiB。
  • 512 KiB 上限是推测。Codex turn/start 和 Claude Code SDK 接受的单条用户消息上限没有实测。MR-3 的真实 Runtime 验收要先测这个数。
  • 裁剪顺序：
    1. 最新一个 Turn 先放进去。
    2. Session 的第一条用户提问放进去（按 8192 / 4096 / 1024 码点裁剪）。它是原始意图。t3code 也固定保留它。
    3. 从新到旧逐个加入整个 Turn。
    4. 放不下时，先删这个 Turn 的工具摘要，再按同样的规则裁剪它的 user 和 response。
    5. 还放不下，就丢掉它和更旧的 Turn，计入 omittedTurns。
    6. 最新一个 Turn 自己就超预算时，对最长的一项做头尾裁剪。
  • 生成后对全文执行 redactSecrets，再用 containsContextSecret 检查本次 Run 的凭据（src/chat/events.ts）。旧记录是用当时的凭据脱敏的，凭据可能已经轮换。

3.4 送达

三个 Runtime 用同一个位置：本次 Turn 的用户消息前缀。插入点是 native.ts:283 的 runtimeUserMessage(...) 的结果。

不放进系统提示的理由（读码）：

  • Codex 的 developerInstructions 和 Claude Code 的 systemPrompt 属于 launchKey（codex-app-server.ts:71-77，claude-code.ts:81-85）。把 handoff 放进去会让常驻进程每个 Turn 都换 key，并且以后每个 Turn 都重复带上。
  • 用户消息只进入原生 transcript 一次。之后它随 checkpoint 保存，由 Runtime 自己的 compaction 处理。

Runtime 送达 细节

3.5 新的原生会话 ID 怎样替换旧的

现状（读码）：sameNative 禁止 Session 换原生会话 ID（store.ts:182-185）。checkpoint 的 head 文档保存旧 ID 和分片列表（context.ts:28,393-423）。

新增 ChatStore.resetNative(actor, runId, record)。它走 mutateRun，所以受租约保护（store.ts:662）。一个事务里做四件事：

  1. 把 rook_chat_session_v2.native_session_id 和当前 Run 的 native_session_id 置空。Session 的 revision 加一。
  2. 把 native-context head 文档写成重置标记：{ version: 3, reset: { runId, previous: { nativeSessionId, bytes, sha256 }, at } }。旧分片不删。
  3. 删除这个 Session 各 Run 的 content_kind='fork-point' 行。旧回复的分支点指向旧原生会话，重建后不可用（store.ts:450-458，context.ts:187-200）。删掉后 Web 不再对旧回复显示分支入口（推测，没有读 Web 的显示条件）。
  4. 追加一条恢复记录（见 5.2）。

NativeContexts.head() 把 version 3 读成「没有 checkpoint，可以新写」。open() 在 Session 没有原生会话 ID 时返回 undefined。write() 对三个 Runtime 都接受在重置标记之后写新 Manifest。现有的「revision > 0 且 value 为空就报 native_context_unavailable」（context.ts:214,397）保持不变。它继续拦截真正读不出来的 head。

之后新原生会话 ID 走已有路径绑定，不需要新代码：

  • Pi：onSession → contexts.bind → recordNativeSession（manager.ts:527-536，context.ts:311-318）。
  • Claude Code、Codex：finishRun 的 checkpoint 分支写入 checkpoint.nativeSessionId（store.ts:714-719）。

本地状态由 executor 清理：

  • Pi：调用已有的 discardLocalContext（isolated.ts:151-160）并停掉这个 Session 的 worker。
  • Claude Code、Codex：每个进程用新的 CODEX_HOME 或 CLAUDE_CONFIG_DIR（native.ts:177-183），没有本地残留。常驻进程必须关闭。NativeExecutor.forget（isolated.ts:638-644）现在只管 Pi，MR-3 要让它也关闭 ClaudeResidentSlot 和 CodexResidentSlot。这同时修掉 chat-lifecycle.md 的 G1。

4. 一个 Turn 的状态机

4.1 状态

状态 含义
accepted Run 已建，状态 running，租约在手。
preparing Rook Backend 读 Session、checkpoint head 和覆盖标记。
resuming Runtime 用已有的原生会话启动。Turn 还没开始。
running Runtime 报告 Turn 已开始（onTurnStarted，native.ts:311；Pi 是第一个事件帧）。
rebuilding Rook Backend 执行 resetNative，清理本地状态。每个 Run 最多进入一次。
running-fresh Runtime 在新原生会话上执行，用户消息带 reason="rebuild" 的 handoff。
finishing Rook Backend 保存 checkpoint，写终态。

4.2 转移

从 事件 到 动作
accepted 开始 preparing
preparing Session 没有原生会话 ID，且没有更早的 Run running-fresh 新 Session。没有 handoff。
preparing Session 没有原生会话 ID，有更早的 Run running-fresh handoff 范围是全部更早的 Run。不写恢复记录，上次重置时已写。
preparing checkpoint 读取成功 resuming handoff 范围是覆盖标记之后的 Run，reason="gap"。范围为空就不加前缀。
preparing 读取失败，错误码属于 5.1 的 A 类 rebuilding
resuming Turn 开始 running
resuming A 类错误 rebuilding Turn 没开始，没有副作用，可以安全重来。
running A 类错误，pending_tools = 0，本 Run 还没重建过 rebuilding handoff 包含本 Run 已落库的事件。MR-4 才做。
running A 类错误，pending_tools > 0 finishing 沿用现有规则，终态 interrupted，execution_tool_result_unknown。这一项仍然显示给用户，见 5.3。
rebuilding resetNative 提交 running-fresh
rebuilding resetNative 失败 finishing 终态 failed，native_rebuild_failed。
running-fresh A 类错误 finishing 终态 failed，native_rebuild_failed。不再重试。
running、running-fresh Runtime 返回结果 finishing
finishing checkpoint 保存成功 终态 覆盖标记前进到本 Run。
finishing checkpoint 保存失败，错误码属于 5.1 的 B 类 终态 Run 保留 Runtime 的结果。同一事务里执行 resetNative。下一个 Turn 自动走 handoff。
任意 Stop finishing 见 4.4。

「是否需要 handoff」不是存下来的标志。它每次从两个事实推出来：Session 有没有原生会话 ID，覆盖标记指向哪个 Run。重建被任何事情打断，下一个 Turn 都会得到同样的判断。

4.3 失败或 Stop 的 Turn 怎样进入下一个 Turn

三个候选我都保留了，按顺序尝试：

  1. 保留原生进程，并在非成功终态保存 checkpoint（主路径）。 Runtime 干净地给出终态时，Rook Backend 读出原生 context，和成功时一样保存。常驻进程不关。
    • 依据（实测，codex.md 1.6）：Codex 在失败或中断之后，同一个 app-server 能正常跑下一个 Turn。
    • 依据（读码，codex.md G6、claude-code.md G7）：t3code 和 Orca 都保留失败或中断 Turn 的历史。
    • Claude Code 恢复一个以未配对 tool_use 结尾的 transcript 的行为是推测，MR-2 的测试要用真实 SDK 验证。
  2. 有未知工具结果时不保存。 pending_tools 对不上时保留旧 checkpoint。这是现有规则（store.ts:715）。
  3. 从 MySQL 补（兜底）。 1 和 2 没保存成时，覆盖标记停在更早的 Run。下一个 Turn 的 preparing 把标记之后的 Run 拼成 reason="gap" 的 handoff。

覆盖标记的规则：

  • Manifest 新增可选字段 coveredRunId 和 final。write() 写入时取 session.activeRunId。prepareCompletion（context.ts:324-331，Claude Code 和 Codex 的终态保存）写 final: true。
  • gap 范围是 coveredRunId 之后创建的 Run。final 不为真且那个 Run 的终态不是 succeeded 时，那个 Run 也算进去，并标 mayOverlap。这是 Pi 在 Turn 中途保存后失败的情况。
  • 旧 Manifest 没有 coveredRunId。gap 范围按空处理，行为和今天一样。
  • Pi 只在 context 确实从 MySQL 加载时才加 gap 前缀。Pi 的本地 JSONL 可能比 MySQL 新（native.ts:139-165）。那时本地文件已经含有这些 Run，再加前缀会重复。所以 handoff 作为选项传给 executeNative，由它在 native.ts:165 的 load() 分支决定是否使用。Claude Code 和 Codex 的常驻进程只在 contextSha 等于 MySQL checkpoint 时复用（codex-app-server.ts:437，claude-code.ts:316），所以它们总是使用。

4.4 与 Stop 的竞争

时刻 结果
Stop 落在 preparing 或 rebuilding，resetNative 提交之前 Run 终态 stopped。原生会话 ID 还在。下一个 Turn 重新尝试恢复，再失败就重建。
Stop 落在 resetNative 提交之后，新原生会话绑定之前 Run 终态 stopped。Session 没有原生会话 ID。下一个 Turn 走「没有原生会话 ID，有更早的 Run」，再次带全量 handoff 启动。Pi 已有的 unboundStop 清理（isolated.ts:578-589）继续适用。
Stop 落在 running-fresh 中 和普通 Turn 的 Stop 一样。按 4.3 保存 checkpoint。保存成功后新原生会话已绑定，handoff 已在它的 transcript 里。
Stop 赢了终态竞争（chat-lifecycle.md G4） 现状（读码加实测）：finishRun 只在 current.state === 'running' 时保存 checkpoint（store.ts:714）。MR-2 去掉这个条件。终态仍是 stopped，checkpoint 照常保存。
Stop 15 秒超时，worker 被杀 没有 checkpoint。下一个 Turn 用 gap handoff 从 MySQL 补。Pi 的本地 JSONL 通过 readExtendedCheckpoint 校验后沿用，校验不过就丢弃（native.ts:602-623）。
失去租约的 Rook Backend 调用 resetNative mutateRun 的 fence 拒绝（store.ts:662-674）。

4.5 与 Queue 的关系

  • 重建发生在一个 Run 内部。Session 的 active_run_id 一直被占着。Queue 派发和新的提交都会被 session_busy 挡住，所以不需要额外的锁。
  • 现状（读码）：上一个 Run 不是 succeeded 时，Queue 以 chat_queue_run_ended 暂停（manager.ts:204）。重建成功的 Run 终态是 succeeded，Queue 继续派发。
  • Queue 里排着的消息不受影响。它们的 prompt 原文在 Queue 里，派发时各自成为新 Run。
  • 插话有一个要验证的点。onControlReady 通过 registered 只 resolve 一次（manager.ts:410-411,496）。一个 Run 里执行两次 Runtime 时，第一次的 control 可能已经登记。MR-3 要保证只登记最后一次的 control，并用测试覆盖「重建期间插话」。在此之前这是推测的风险。
  • 中断重排（CONTEXT.md）不变。重建成功的 Run 不是 interrupted。

5.2 记录在哪里

主记录：rook_chat_run_content_v2，content_kind='recovery'，chunk_index 在一个 Run 内递增。content_kind 是 VARCHAR(16)，content 是 VARCHAR(2000)（deploy/schema.sql:88-99）。不需要改表，所以不走 RDS 审批。

{"v":1,"at":"2026-11-28T10:00:00.000Z","kind":"rebuild","phase":"resume","code":"native_context_unavailable",
 "runtime":"codex","previousNativeSessionId":"…","handoff":{"turns":12,"omittedTurns":3,"bytes":48211,"sha256":"…"},
 "detail":"thread/resume rejected"}
  • kind 取 rebuild（立即重建）、reset（B 类延后重建）、gap（用了 gap handoff）、checkpoint_skipped（非成功终态没能保存 checkpoint）。
  • detail 最多 500 字符，经过 errorDetailText 脱敏。记录里没有 handoff 正文，没有凭据。
  • 现有读取都按 content_kind 精确匹配（store.ts:106,377,454,478,594,632,651）。分支复制只复制 prompt、response、fork-point（store.ts:478）。所以新的 kind 不会进入任何 API 响应、分享或使用统计（读码）。
  • 运维查询：SELECT run_id, content, ctime FROM rook_chat_run_content_v2 WHERE mtime >= ? AND content_kind='recovery'。它走已有的 ix_mtime。

为什么不用 rook_chat_run_error_v1（读码）：

  • 它有 UNIQUE KEY uk_run_error (run_id)（deploy/schema.sql:67）。一个 Run 先写了恢复记录、后来又真的失败时，finishRun 的 INSERT（store.ts:733）会冲突，整个终态事务回滚。
  • getRun 不看 Run 状态就把这张表的 error_detail 返回给 owner（store.ts:557-558）。SESSIONS.md 写明它「在页面显示」。恢复记录放进去会暴露给用户。

第二处记录：重置后的 head 文档保留旧原生会话 ID 和旧 checkpoint 的 sha256。旧分片不删，运维可以取证。

第三处：Rook Backend 打一行 console.error('native_context_rebuilt', code)，沿用现有风格（isolated.ts:157）。它只含错误码。

6. 我替用户做的决定

6.1 重建时显示一行中性提示，不是完全静默

理由：重建后模型只有提问、回复和工具摘要。它可能记不住早先的细节。完全静默时，用户会看到模型「突然失忆」而找不到原因。这一行沿用压缩的显示，不是错误，符合「错误不要暴露」。t3code 也显示一个中性条目。想改成完全静默时，去掉 rebuild 这对事件即可。

6.2 handoff 不调用模型做摘要

理由：三个先例都不做。Rook Backend 没有 Runtime 无关的模型调用入口，新增它会带来 Provider 选择、计费和失败处理。按预算裁剪是确定的，可以用字面值测试。

6.3 native_model_context_budget 当次仍显示，但同时重置原生 context

理由：模型这次没有产出，把 Run 标成成功是说谎。自动在新原生会话上重跑属于 4.2 的「running 中重建」，放在 MR-4。MR-4 落地后这一项也会变成隐藏的恢复。

10. 风险

风险 标签 处理
保存了失败 Turn 的 transcript 后，每次恢复都被 Provider 拒绝，形成循环 t3code 对 Codex 的 invalid_encrypted_content 有专门处理（读码）。Rook 上会不会发生是推测 MR-4 加一条规则：同一个原生会话上连续两个 Run 失败且都没有任何 assistant 输出时，finishing 执行 resetNative。这条规则不依赖具体错误文本。

单条用户消息上限未知 推测 MR-3 验收时实测，校正上限。
