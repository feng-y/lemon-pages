Rook 多机执行归属

多台 Rook Backend 共用一个 MySQL 时，一项工作该由谁执行。目标是优先交给上次处理的机器，pod 不丢就继续。依据是当前 main 的代码和公开系统的原始文档。

TL;DR

现在任何 Backend 都能抢任何工作，没有一项工作记录该由谁处理，旧版本也会按旧语义执行新工作。三套方案都保留现有的 FOR UPDATE 和 active_run_id 来保证只执行一次，区别在于亲和怎么判活。推荐先做方案 C（粘性派发加超时回落，Temporal 式）。它不加表，不写心跳，pod 丢失后约 5 秒交接（推断）。要做机器视图和按能力拒绝入队时，再加方案 A 的实例心跳表。三套方案都必须先解决旧版本：Rook 正式环境升级一次，再用能力门槛防止以后复发。

  • MySQL 里只执行一次已经有保障（实测代码）。Session 行锁加 active_run_id 校验，作用接近 Kleppmann 说的 fencing token。校验和写入在同一个 MySQL 事务里，丢了租约的 Run 续不上，也写不进 Run 状态。MySQL 之外的副作用不受这层保护，比如卡顿后的旧 Run 仍可能调用一次连接器（推断）。
  • 缺的是归属（实测代码）。Run 结束后 active_run_id 清空，Session 不记得上次在哪台机器跑。下一项工作由谁的 1 秒轮询先到决定。
  • 缺的是版本门槛（实测线上）。Multica 发布后，tools 为空的 RK-24 业务用例仍拿到了凭据。原因是旧版本 Backend 也在领取共享工作，它会丢掉不认识的 Queue 字段，限制就失效了。

  • 只有 Akka 和 Temporal 主动把工作从旧版本引开。Multica 的能力检查发生在领取之后，缺能力就让任务失败（实测源码 server/internal/handler/daemon.go:2931）。
  • 租约不等于互斥。client-go 和 Kleppmann 都说明，租约只是「大概率只有一个」。真正的互斥要落在存储的校验上，在 Rook 里就是 Session 行锁和 active_run_id。

三套方案

三套都只在 Queue 派发这一层做亲和。Kanban 占批次和自动化落定时调用都是很短的 CAS，谁做都一样，只加能力门槛。

方案 A：实例心跳表加执行机器

Multica、Orleans 式
  • 数据。新表 rook_backend_instance_v1，每个 Backend 实例一行：instance_id（pod 名加启动 UUID）、commit、capabilities、heartbeat_at、draining。每 5 秒写一次心跳。rook_chat_session_v2 加一列 executor_instance，Run 结束后保留。
  • 领取规则。在 beginRun 已有的事务里判断。执行机器是我，就继续。执行机器是别人且心跳在 30 秒内，就跳过。心跳过期、对方 draining、或对方缺这项工作要的能力，就用 CAS 改成自己。没有执行机器，就按现在的规则抢。
  • 好处。严格满足「pod 不丢就继续」。有一张实时的机器表，能看到哪些 commit 在线。入队时能按能力拒绝，没有合格机器在线就直接报错，不让工作挂着没人领。这和 Orleans 成员表、Multica runtime 表是同一类做法。
  • 代价。一张新表和一列，都要 DDL 审批。pod 丢失后最多 30 秒才交接。执行机器满载时，它名下的 Session 也只能排队等它。

方案 B：Session 执行租约

Kubernetes Lease 式
  • 数据。rook_chat_session_v2 加 executor_instance 和 executor_until。没有实例表。
  • 领取规则。持有者每 5 秒用一条 UPDATE ... WHERE executor_instance=? 给自己名下的 Session 续约，只续还有常驻 Pi worker 的那些。租约在有效期内，别人跳过。租约过期，谁都可以 CAS 抢。SIGTERM 时一条语句清空自己的租约，立刻交接。
  • 好处。亲和只在热状态还在时生效。worker 被回收，租约自然到期，不会把 Session 绑在一台没有缓存的机器上。
  • 代价。续约写入量随热 Session 数增长。看不到机器视图，也做不了入队时的能力拒绝。和方案 C 比，多出来的只是「worker 在就一直留着」，收益不大。

方案 C：粘性派发加超时回落

推荐先做Temporal sticky 式
  • 数据。Run 结束时，在这个 Session 的 Queue 文档里记下 executor（pod 名加启动 UUID）。Queue 已经是 JSON 文档（src/chat/queue.ts:17 的 chat-queue），不需要 DDL。
  • 领取规则。Queue 项就绪后的前 5 秒，只有 executor 本人能领。过了 5 秒，任何有能力的 Backend 都能领。真正的互斥仍然是 beginRun 的行锁。
  • 为什么够用（推断）。执行机器活着时每秒轮询一次，5 秒窗口里它有 5 次机会先领到。它丢了，5 秒后别人接手，比心跳方案的 30 秒快。pod 重启后启动 UUID 变了，亲和自动失效，这时内存里的 worker 也确实没了。
  • 代价。没有存活判断，执行机器满载或卡顿超过 5 秒，工作会被别人领走，只损失缓存，不影响正确性。看不到机器视图。

共同前提：旧版本不能领新工作

三套方案都只约束遵守规则的新版本。已经在线上的旧版本看不到这些规则。

  • 能力门槛。每个 Backend 启动时声明 capabilities，比如 agent-tools-v1。新语义的工作带 requires。领取前核对自己有没有这些能力，没有就不领。能力按名字声明，不比版本号，这一点沿用 Multica 的 X-Client-Capabilities。Multica 缺能力时让任务失败，Rook 改成不领，和 Akka 滚动发布时不往旧节点分配一致。
  • 旧版本只能升级。门槛对旧代码无效。旧版本会丢掉不认识的字段，再按旧语义执行。所以 Rook 正式环境要先发布一次带门槛的版本，之后的混跑才受保护。
  • 换 scope 名不够（推断）。Queue 换成新 scope，旧版本确实看不到新 Queue 项。但旧版本还会占 Kanban 批次、触发自动化，再写进旧 scope 自己执行。要把所有入口都换掉，等于一次数据迁移，不如升级。

推荐和顺序

推荐

先做能力门槛和方案 C。它不需要 DDL 审批，改动集中在 Queue 派发。以后需要机器视图，或者需要「没有合格机器就拒绝入队」，再加方案 A 的实例心跳表。C 的 executor 字段可以直接沿用。

  1. 在 release_fix/backend-affinity-20261127 上实现能力门槛：启动时声明 capabilities，Queue、Kanban、自动化三个入口核对 requires。
  2. 实现方案 C：Run 结束写 executor，派发时按 5 秒窗口判断。
  3. 写测试，用业务用例：同一个 Task 会话连续两次跟进落在同一台；执行机器停止后 5 秒由另一台接手；缺能力的 Backend 不领 tools 为空的工作。
  4. Multica 和 Rook 正式环境都发布后，重跑 RK-24（tools 为空对比 ['*']）和定时任务 SSO 检查。
未验证和风险

5 秒窗口、30 秒心跳都是按现有 1 秒轮询和 30 秒 Run 租约推出来的，没有线上实测。Run 结束后 Session 再执行时能复用多少热状态，没有量过，亲和的收益是推断。发布 Rook 正式环境需要单独确认。在它升级之前，tools 为空的限制在线上仍然不可靠。
