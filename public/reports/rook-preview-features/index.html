预览功能开关

Rook 按用户开放页面和功能的三套方案。三套都只控制页面可见，不做服务端权限。

TL;DR

三套方案共用一个通用机制。每个页面、按钮或菜单项的接入方式相同：功能清单 previewFeatures 加一行，入口加一个 identity.features.includes('key') 判断，/api/me 返回当前用户可见的功能键。

三套方案的区别在于授权存在哪里，以及管理员在哪里操作。方案一在用户列表加一列，改动最小。方案二新增「功能开放」页，按功能管理名单，授权仍记在用户准入记录上。方案三也新增「功能开放」页，授权单独存成一份功能配置，另外支持不发布就对所有人开放或收回。

推荐方案三。原因有两个：它按功能保存名单，和管理员「把某个功能给几个人」的操作方式一致；功能开放后出了问题，不用发布就能收回。

共用机制

这部分三套方案完全相同，决定了它是通用的。

// src/features.ts，前后端共用
export const previewFeatures = {
  'native-runtimes': 'Claude Code 和 Codex',
  agents: '智能体',
} as const;
export type PreviewFeature = keyof typeof previewFeatures;

// GET /api/me 增加
features: PreviewFeature[]   // 管理员拿到全部键

// 前端入口
{identity.features.includes('agents') && <AgentsEntry />}
  • 接入一个功能只要两行。清单加一行，入口加一个判断。管理界面按清单自动生成，不用为每个功能改界面。
  • 下线时不用迁移数据。服务端读取授权后与清单取交集，删掉清单里的键之后，残留的授权数据会被忽略。
  • 不是安全边界。开关只隐藏入口，避免用户误用还没测完的功能。普通用户直接调用接口仍然能用。需要真正限制的功能，在服务端单独校验。
  • 不合并现有的 managementTabs。反馈管理在服务端有校验，属于权限，不归这套开关管。

方案一：用户列表加列

授权记在用户准入记录上，管理员在现有的用户列表里逐个勾选。

项内容
存储AdmissionUser.features?: PreviewFeature[]，和 managementTabs 存在同一份记录里
写入现有的用户更新接口 PUT 增加 features 字段。不带这个字段时保留原值
改动文件src/features.ts、src/user-admission.ts、src/server.ts、web/main.tsx、web/user-admission.tsx
优点改动最小，没有新页面，也没有新存储
缺点给 10 个人开放同一个功能要打开 10 行。看不出某个功能现在开放给了哪些人。功能多了以后这一列会很挤

方案二：按功能管理名单

存储与方案一相同，但管理员在「系统管理 → 功能开放」里按功能管理名单。

项内容
存储与方案一相同，AdmissionUser.features
写入添加或移除一个用户时，对这个用户调用一次 PUT。并发冲突沿用 409 configuration_conflict
改动文件方案一的服务端文件，另加 web/preview-features.tsx 和 web/management.tsx
优点能直接看到每个功能开放给了谁，适合「把某个功能给几个人」
缺点界面按功能组织，数据却按用户存，一次批量添加要发多次请求。用户准入记录多了一个和准入无关的字段

方案三：功能开放配置

每个功能单独记录开放范围，单独存成一份配置文档。管理界面与方案二相同，每张卡片多一个开放范围选择。

// ConfigurationStore 中新的一份文档 'preview-features'
type FeatureAccess = { scope: 'admins' | 'listed' | 'everyone'; users: string[] };
type PreviewFeatureConfig = Partial<Record<PreviewFeature, FeatureAccess>>;
// 清单里有、配置里没有的功能，按 { scope: 'admins', users: [] } 处理
项内容
存储ConfigurationStore 中新的一份文档，带 revision。不改用户准入记录
写入新增管理员接口 PUT /api/admin/preview-features，一次保存一个功能的开放范围和整份名单。revision 不一致时返回 409
读取/api/me 读取这份文档，与清单取交集，再按当前用户计算可见的功能
改动文件src/features.ts（同时放读写函数）、src/server.ts、web/main.tsx、web/preview-features.tsx、web/management.tsx
优点按功能存、按功能改，和界面一致。批量添加只写一次。开放后出问题可以不发布就收回。不碰用户准入
缺点多一份配置文档和一个管理员接口。功能处于「所有人」时，代码里的开关还在，需要记得在下次发布时删掉

推荐与首批接入

推荐方案三。管理员的实际操作是「把某个功能开放给一批人」，方案三的存储、接口和界面都按功能组织，一次保存一个功能。功能对所有人开放后如果发现问题，管理员可以直接切回「指定用户」，不用发布。代价是多一份配置文档，和方案二相比改动文件数差不多。

如果只想要最快上线，选方案一。之后需要按功能管理时，可以再迁移到方案三，迁移时只需要把每个用户的 features 转换成每个功能的名单。

功能键入口现在接入后
native-runtimesChat 的 Runtime 选择器只有管理员能选 Claude Code 和 Codex。无法开放给部分用户按开放范围决定。没有开放的用户看到两项置灰。已建好的 Session 继续可用
agents设置页的「智能体」所有通过准入的用户可见按开放范围决定，没有开放的用户看不到入口
智能体入口会对现有用户收起

接入发布后，智能体默认只对管理员可见。如果需要保留现有的使用者，发布后先把它设成「所有人」，或者把现有使用者加入名单。方案一和方案二需要在发布前逐个勾选。

验证计划

  • 服务端测试。写入后能读回。清单外的键返回 400。删掉清单里的键之后，残留授权被忽略。分别核对管理员、名单内用户、名单外用户和没有准入记录的用户，/api/me 返回的 features 是否正确。方案三另测三种开放范围的切换，以及 revision 冲突。
  • 界面测试。沿用现有的 Runtime 选择器测试，把判断条件从「是否管理员」改为「是否有 native-runtimes」。
  • 浏览器验收。用真实构建分别以管理员、名单内用户和名单外用户登录，检查 Runtime 选择器、智能体入口和「功能开放」页。
  • 常规检查。运行 npm run check、完整测试和 npm run build。
