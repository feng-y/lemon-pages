目标

Rook 自己写什么、交给 Runtime 什么，以及多用户这层怎么落。

  • Runtime 驱动对齐 t3code 和 Orca。Pi 保持 persistent worker；Claude Code 每个 Session 一个常驻 query()；Codex 每个 Session 一个常驻 app-server。压缩、skill、历史和子代理都交给 Runtime 自己处理。
  • Rook 只写多用户这一层。Session 的执行 UID 隔离、ClawSec 与用户 SSO 的绑定、Queue、定时任务、智能体的 owner 身份。这些是 t3code 和 Orca 都没有的。
  • 冻结与恢复的体验要和「进程还在」一致。空闲会话可以被回收，下一次发消息要能接上原生会话；不接上 MySQL 没保存的内容。
  • 顺序是 Pi 先做完、验收、合并，再做 Claude Code 和 Codex。用户 2026-11-27 明确了这个顺序，并要求先部署验证、验证通过再推进后续合入。
  • 不要限制活跃会话。通过扩容和冻结不活跃会话控制资源；活跃 Turn、待审批、后台任务或 Queue 有消息时不算空闲。

方案

三个 Runtime 共用一套常驻、冻结、恢复和工具边界。下面是已经落到代码里的部分。

常驻进程与复用

  • 一个 Session 一个进程。Pi 是 persistent worker；Claude Code 持有一个 query()，后续消息走 streaming input；Codex 持有一个 codex app-server --stdio 和一个原生 thread，每个 Turn 调一次 turn/start。
  • 复用 key 按内容算，不按 Run 算。model、effort、token hash、skill 名加 sha256、系统 skill 根目录、定时 MCP 授权工具名。不含 runId、快照路径、socket 目录和 CODEX_HOME。key 变了就换进程，并用原生 resume 接上。
  • supervisor 接受新的 pid。常驻进程一生中可能换 pid，旧的退出后新的要能被接管；clean <pid> 只清豁免，不杀进程。

冻结与恢复

  • 失败的 Turn 删除本地文件。保存失败的 Run 不留给下一个 worker；下一轮从 MySQL 恢复，不会接上没保存的内容。
  • Stop 和失败都关掉常驻进程。Claude Code 调 interrupt()，Codex 发 turn/interrupt；1 秒内没结束就关进程。下一轮从 MySQL 恢复，不接被停掉那一轮的内容。
  • 冻结不设 30 分钟计时器。实现上只在空闲 worker 超过 ROOK_CHAT_MAX_IDLE_WORKERS（默认 4）时踢走最早空闲的那个。方案文档第 3.1 节仍写着「空闲 30 分钟冻结」，与代码不一致，需要改文档。

工具边界

  • 三个 Runtime 用同一条边界：执行 UID。Chat Run 放开全部工具：Pi 传 tools: 'all'，Claude Code 用 bypassPermissions 加 allowDangerouslySkipPermissions，Codex 用 danger-full-access。
  • 定时 Run 保持受限。带 runContext 的 Run 保持 read-only 或原来的工具限制，看不到 Bash。
  • Claude Code 在 root 下拒绝 bypassPermissions。这是实测；生产 Run 用非 root 执行 UID，所以不受影响。两个直接以 root 调用的测试改成 restrictedTools。

Codex 流空闲上限（修复分支）

  • Provider 配置加 stream_idle_timeout_ms=120000。模型流 120 秒没有数据时 Codex 自己重试，重试用尽后 Turn 失败。保留 Codex 原生 5 次重试，最坏约 12 分钟；Pi 是 120 秒 × 3 次，最坏约 8 分钟；Codex 默认是 300 秒 × 5 次，最坏约 30 分钟。
  • 没有扩大事件映射。Codex 的工具步骤和流式文本事件沿用原有行为；error 的 willRetry 映射成前端重连提示仍是 TODO。
