Rook 多机执行归属

多台 Rook Backend 共用一个 MySQL 时，一项工作该由谁执行。目标按优先级排：用户响应快、执行成功率高、Session 留在上次执行的机器上。依据是 Rook main 的代码、Sage 与 Multica 源码、Codex App Server 源码和公开系统的一手资料；方案经过一轮对照代码的独立 review。

TL;DR

会话目录在容器本地盘上，换机器就没有了；原生 context 存在 MySQL，换机器能恢复。所以跟着机器走的单位是 Session，不是用户。推荐每台 Backend 每 5 秒写一行心跳，Session 记下上次的执行机器。那台还活着，就只由它执行；它丢了、draining 或缺能力，任何没满的机器都能接手。新 Session 交给任何没满的机器，扩容的 pod 立刻能接到。Chat 和离线任务组用同一条规则，离线任务按任务分发，每个任务落到它的 Task 会话。成功率另靠五件事：能力门槛、满载不报错、单用户上限按全局统计、发布时排空、离线任务中断后安全重排。只执行一次仍靠现有的 FOR UPDATE 和 active_run_id。

  • 只执行一次已经有保障（实测代码）。Session 行锁、active_run_id 校验和 Queue 消费在同一个 MySQL 事务里（src/chat/manager.ts:191-193），作用接近 Kleppmann 说的 fencing token。MySQL 之外的副作用不受这层保护（推断）。
  • 会话文件只在执行过的机器上（实测）。/data 是容器本地盘，不挂数据卷，Pod 替换后重建（deployment.md:771）。会话仓库根是同一 Session 所有 Run 共用的目录（CONTEXT.md:65）。原生 context 的 checkpoint 只存 MySQL（CONTEXT.md:57），换机器能恢复，文件不能。今天 Multica 和 Rook 正式环境共用 MySQL，一个 Session 的下一条排队消息可能被另一个部署领走，在那边看不到上次的文件（推断）。
  • 满载直接报错（实测代码）。直接发送碰到本机 activeRuns（默认 4）或单用户上限，返回 503 chat_run_overloaded（src/chat/manager.ts:277-282），即使别的机器空着。
  • 并发上限是单机的（实测代码）。userActiveRuns（默认 2）只统计本机（src/chat/manager.ts:281）。智能体 Run 的 actor 是 runAs（src/agent-tasks.ts:328），内置 Rook 的全部跟进和管理员自己的 Chat 共用这 2 个名额。
  • 发布会打断离线任务且不重跑（实测代码）。智能体批次落成「智能体运行中断。」（src/agent-tasks.ts:393-395），Queue 暂停（src/chat/manager.ts:173-175）。
  • 旧版本不看任何新规则（实测）。Multica 发布后，tools 为空的 RK-24 用例仍拿到了凭据。旧代码派发全部 target（src/chat/manager.ts:148-150），丢掉不认识的 Queue 字段。
  • 浏览器不固定连一台机器（实测）。SLB 上只有一条 / 路由，没有 hash 或 cookie。SSE 从 MySQL 每 200 毫秒读事件（src/chat/api.ts:283-307），停止走 MySQL 的 stopping 加续约检查（src/chat/store.ts:617、:708），所以接请求的机器不必是执行的机器。

推荐：Session 跟着执行机器

一条规则覆盖 Chat 和离线任务组。Session 的文件在哪台机器，下一次就在哪台执行。

实例心跳加 Session 执行机器

推荐由方案 A 演变，Orleans、Multica 式
  • 数据。新表 rook_backend_member_v1 每台一行：instance_id（pod 名加启动 UUID）、capabilities、draining、heartbeat_at，每 5 秒写一次，15 秒没更新算丢失。Session 加一列 executor_instance，beginRun 在已经锁住的 Session 行上顺手写入，不多一次事务。
  • 规则。执行机器还活着、没有 draining、有这项工作要的能力，就只由它执行，它满了也等它。否则任何能力合格、没满的机器都能执行，执行时写成自己。新 Session 没有执行机器，谁先领谁执行。
  • 为什么满了也等。换机器会丢掉会话文件，Agent 找不到上一轮写的东西，比多等一会儿更伤成功率。一台不会忙到卡死，因为每台有 activeRuns 上限，新 Session 会落到别的机器。
  • 扩容。新 pod 一上线就能领新 Session 和丢了执行机器的 Session，不需要重平衡。已有 Session 不迁移。
  • 发布。SIGTERM 时先把自己标 draining，别的机器下一秒就能接新工作。Pod 替换后本地盘重建，旧 Session 由谁先领谁执行，原生 context 从 MySQL 恢复。

  • 不按用户绑定（推断）。按用户绑定的收益是常驻 Pi worker 和本地文件。文件按 Session 存，原生 context 在 MySQL，所以 Session 粒度已经拿到主要收益。常驻 worker 的冷启动代价没量过。按用户绑定还会把内置 Rook 的全部跟进压到一台。
  • 不做一致性哈希和重平衡（推断）。每个应用一个副本（deployment.md:328），每次发布实例身份都会变。新 Session 谁有空谁领，已经能把负载摊开。
  • 代价。一张表加一列，要走 DDL 审批。执行机器满载时，它的 Session 要排队。

成功率：另外五件事

归属解决「在哪执行」。下面五件事解决「会不会失败」，按影响排序。

备选方案

讨论过、没有采用的四套方案。

方案 D：owner 绑定

微信 seqsvr 式
  • 做法。每个 owner 一行带租约的绑定，Chat、智能体跟进、定时任务都按运行身份找绑定的机器。满载时溢出到别的机器。
  • 没采用的原因。溢出会让 Session 离开它的文件。内置 Rook 以管理员为运行身份，全部跟进集中到一台。

方案 D 加一致性哈希和重平衡

Slack、Discord 式
  • 做法。新 owner 按 Rendezvous 哈希放到没满的成员上，副本数稳定变化后释放空闲且目标已变的绑定。
  • 没采用的原因。一个副本、频繁发布时，亲和只在两次发布之间有效，重平衡的稳定窗口还要挡住 maxSurge 和崩溃重建。

方案 B：Session 执行租约

Kubernetes Lease 式
  • 做法。Session 加 executor_instance 和 executor_until，持有者给还有 Pi worker 的 Session 续约。
  • 没采用的原因。续约写入随热 Session 数增长；租约一过期，文件还在的 Session 也会被领走。

方案 C：粘性派发加超时回落

Temporal sticky 式
  • 做法。Run 结束时在 Queue 文档里记 executor，5 秒内只有它能领。不需要 DDL。
  • 没采用的原因。没有存活判断，执行机器卡顿超过 5 秒，Session 就会离开它的文件。直接发送不受约束。

顺序和风险

按对成功率的影响排序，每一步单独可验收。

  1. 能力门槛：启动时声明 capabilities，Queue、Kanban、自动化三个入口核对 requires。发布 Rook 正式环境，再打开 queueWrites。
  2. 满载不报错：直接发送碰到上限时入队并返回 requestId，Web 按它跟进 Run。
  3. 单用户上限按全局统计，智能体 Run 单独名额。
  4. 发布排空，离线任务在没调用工具时中断就重排一次。
  5. 按 RDS 规范写 rook_backend_member_v1 和 executor_instance 的 DDL，过 npm run rds:check 和线上 sql_check，提交审批，再实现执行机器规则。
  6. 用业务用例验收：同一 Session 的连续消息落在同一台；执行机器停止后另一台接手；满载时直接发送不再 503；缺能力的 Backend 不领 tools 为空的工作。两个环境都发布后重跑 RK-24 和定时任务的 SSO 检查。
未验证和风险

15 秒心跳过期、10 分钟 requires 超时是参考 Kubernetes 和经验取的，没有实测。activeRuns=4 和单台 16 核 32 GiB 的实际承载力没有量过，调高上限可能是改善排队最便宜的办法。常驻 Pi worker 的冷启动代价没量过。Pod 的退出宽限期没查。Rook 正式环境升级之前，tools 为空的限制在线上仍然不可靠。
