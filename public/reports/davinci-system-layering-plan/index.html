1. 输入怎么进计划

读的是 brooks-lint 的 README、brooks-audit/architecture-guide.md，和 ub-mode 的 SKILL.md。没有运行它们的伴生工具（crapper、dryer、mutator 在本机未装，也没核实支持 C++），所以不把它们列为 gate。

来源规则 在本计划里的落点
Brooks 概念完整性：一个设计思想贯穿全系统 全系统只有一个思想：能力代码只经「中间件入口」碰外部系统。每个波次只是把一个外部系统纳入这个思想
brooks-lint 的 Symptom → Source → Consequence → Remedy 每个切片的「证据」列按这四段写，不写没有后果的症状
brooks-lint 的 edge-and-change witness（说出受影响的边和一次具体改动） 每个切片写出「改前加这个需求要动哪些文件，改后动哪些」，作为验收例子
brooks-lint：未知不等于干净，缺决定性证据就标 unassessed §6 列未核实项，对应切片开工前先关掉，不假设为真
brooks-lint sweep：修复轮次有上限，报告停止原因 每个 MR 本地 CR-Rot 最多 3 轮，仍有「主要」以上意见则停下报告
ub-mode：一个决定只放一处 声明表是同一事实的唯一来源，7 份清单和「replay 不覆盖」清单都从它读
ub-mode：先写会失败的测试，再改代码 每个切片先写检查或测试，看它在 master 上按预期失败，再改
ub-mode：Build the Lever，先做一个单元，再让工具对齐它 S1 先做检查脚本，后面每个切片用它出数字
ub-mode：先删再加；每个单元做完就验证 波 1 先删；每个 MR 只含一个验证单元

3. 粒度规则

依据 harness/core/VERIFICATION_POLICY.md 的 Verification-cost-aware slicing，再加一条上限。

  1. 一个 MR 对应一个验证单元和一个回滚单元。共享同一次 build 和 replay、回滚方式相同的改动合在一起。
  2. 结构相位和行为相位分开。搬、删先合，改行为的另开 MR。
  3. 一个 MR 只收敛一个外部系统，或只动一份清单。
  4. 粒度上限（本文提议，用户可调）：去掉经 move_only.py 证明的纯搬移后，改动不超过 25 个文件。超过就拆，或在 MR 描述写明为什么不能拆。依据是报告第 5 节：55–70 个文件的 MR 超过 bot 的 diff 上限，评审不收敛。
  5. 行为变化的 MR 另外要有一个可观测的失败信号（计数、日志或测试），不靠 replay 通过证明。
  6. 叠放的 MR 每个单独过 bot；上层在下层合入后再开。
