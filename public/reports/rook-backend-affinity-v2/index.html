Rook 多机执行归属

多台 Rook Backend 共用一个 MySQL 时，一项工作该由谁执行。目标：每个用户绑定一台 server，不管在线还是离线；server 丢了由别的机器接手，任务不轮空。依据是 Rook main 的代码、Sage 与 Multica 源码、Codex App Server 源码和公开系统的一手资料。

TL;DR

推荐每个 owner 绑定一台 Backend。owner 就是 Run 的运行身份，Chat、智能体跟进、定时任务都按它找绑定的机器执行。绑定是一行带租约的记录，持有者每 5 秒用一条语句续约。租约过期、持有者 draining 或缺少需要的能力时，任何有能力的 Backend 都能用 CAS 接手，所以任务不会轮空，也不用选主。调研的系统都是一个 key 同一时刻只有一个持有者，持有者丢了就重新指派；没有一个会迁移正在执行的工作。微信 seqsvr 按 uid 段归属一台 AllocSvr，和这个设计最接近。只执行一次仍靠现有的 FOR UPDATE 和 active_run_id。前提不变：先加能力门槛，Rook 正式环境升级一次。

  • MySQL 里只执行一次已经有保障（实测代码）。Session 行锁加 active_run_id 校验，作用接近 Kleppmann 说的 fencing token。校验和写入在同一个 MySQL 事务里，丢了租约的 Run 续不上，也写不进 Run 状态。MySQL 之外的副作用不受这层保护，比如卡顿后的旧 Run 仍可能调用一次连接器（推断）。
  • 缺的是归属（实测代码）。没有任何记录说明一个用户的工作该在哪台机器执行。谁的轮询先到，谁就执行。
  • 缺的是版本门槛（实测线上）。Multica 发布后，tools 为空的 RK-24 业务用例仍拿到了凭据。原因是旧版本 Backend 也在领取共享工作，它会丢掉不认识的 Queue 字段，限制就失效了。
  • 浏览器不固定连一台机器（实测）。Multica 域名在 SLB 上只有一条 / 路由，只开了 websocket，没有 hash、cookie 或 trafficPolicy。浏览器只在看 Run 事件时开 SSE，SSE 所在的 Backend 每 200 毫秒从 MySQL 读事件（src/chat/api.ts:283-307），不需要和执行机器通信。所以执行归属可以和连接完全分开。
  • 并发上限是单机的（实测）。userActiveRuns（默认 2）只统计本机的 Run（src/chat/manager.ts:281）。一个用户的 Run 分散在多台时，总并发可能超过上限。

推荐：用户绑定 server

一条规则覆盖所有工作。在线和离线不分开处理。

方案 D：owner 绑定

推荐微信 seqsvr、Kubernetes Lease 式
  • 数据。新表 rook_owner_binding_v1，每个 owner 一行：owner_key（唯一）、instance_id（pod 名加启动 UUID）、lease_expires_at、revision。
  • 规则。Run 按运行身份（owner）找绑定。绑定的是我，就执行。绑定的是别人且租约有效，就不领。没有绑定、租约过期、持有者 draining 或缺少这项工作要的能力，任何有能力的 Backend 都能用 CAS 绑定到自己再执行。
  • 续约和释放。每台 Backend 每 5 秒用一条 UPDATE ... WHERE instance_id=? 续约自己名下全部绑定，写入量和 owner 数无关，只有一条语句。SIGTERM 时一条语句释放全部绑定，别的机器下一次轮询就接手。
  • 任务不轮空。每台 Backend 的 1 秒 Queue 轮询都会看到没有有效绑定的工作，并把它接过来。不需要选主。机器变多、需要均衡负载时，再按 Kubernetes Lease 的写法抢一个主，由主把新 owner 分给负载最低的机器。
  • pod 丢失。绑定最多 30 秒后过期，正在执行的 Run 由现有的 recoverExpired 标中断，不迁移，和调研的系统一致。
工作在哪执行要改什么
用户直接发送绑定的机器落到非绑定机器的请求不再当场执行，改为入队，由绑定的机器在 1 秒内领取

  • 好处（推断）。同一个 owner 的 Pi worker、uid 目录和仓库缓存都在一台机器上。userActiveRuns 不用改就成了全局上限。机器表也不需要，绑定租约本身就说明持有者还活着。
  • 代价。直接发送落到非绑定机器时，Run 会晚最多 1 秒开始（推断）。新表要走 DDL 审批。
  • 热点（推断）。内置 Rook 以绑定它的管理员为运行身份，所以它在所有 Task 上的跟进都会集中到那位管理员绑定的机器。量大了再改成按智能体绑定。

备选方案

早先按 Session 做亲和的三套方案，留作对照。方案 D 等于把 B 的租约从 Session 换成 owner，续约从「每个热 Session」变成「每台机器一条语句」。

方案 A：实例心跳表加执行机器

Multica、Orleans 式
  • 做法。新表 rook_backend_instance_v1 记每个实例的 commit、capabilities、heartbeat_at、draining，每 5 秒写心跳。Session 加 executor_instance，心跳过期、draining 或缺能力时别人 CAS 接手。
  • 取舍。有机器视图，能在没有合格机器时拒绝入队。一张新表加一列，强杀后最多 30 秒交接。

方案 B：Session 执行租约

Kubernetes Lease 式
  • 做法。Session 加 executor_instance 和 executor_until，持有者只给还有 Pi worker 的 Session 续约，过期后谁都能抢。
  • 取舍。亲和只在热状态还在时生效。续约写入随热 Session 数增长，没有机器视图。

方案 C：粘性派发加超时回落

Temporal sticky 式
  • 做法。Run 结束时在 Queue 文档里记 executor，就绪后 5 秒内只有它能领，之后谁都能领。不需要 DDL。
  • 取舍。没有存活判断，执行机器满载或卡顿超过 5 秒就会被别人领走。只覆盖 Queue 派发，用户直接发送仍跟着 SLB 走。

一致性哈希（Rendezvous）没有列为方案。扩容时它会把一部分用户从还活着的 pod 上移走，违反「pod 不丢就继续」。

共同前提：旧版本不能领新工作

所有方案都只约束遵守规则的新版本。已经在线上的旧版本看不到这些规则。

  • 能力门槛。每个 Backend 启动时声明 capabilities，比如 agent-tools-v1。新语义的工作带 requires。领取和接手绑定前都核对自己有没有这些能力，没有就不领。能力按名字声明，不比版本号，沿用 Multica 的 X-Client-Capabilities；缺能力时不领，而不是像 Multica 那样让任务失败。
  • 旧版本只能升级。门槛对旧代码无效，旧版本会丢掉不认识的字段再按旧语义执行。Rook 正式环境要先发布一次带门槛的版本，之后的混跑才受保护。
  • 换 scope 名不够（推断）。旧版本还会占 Kanban 批次、触发自动化，再写进旧 scope 自己执行。要把所有入口都换掉，等于一次数据迁移，不如升级。

顺序和风险

  1. 能力门槛：启动时声明 capabilities，Queue、Kanban、自动化三个入口核对 requires。
  2. 按 RDS 规范写 rook_owner_binding_v1 的 DDL，过 npm run rds:check 和线上 sql_check，提交审批。
  3. 实现 owner 绑定：续约和释放、Queue 派发先看绑定、非绑定机器收到直接发送时改为入队。
  4. 用业务用例测试：同一个 owner 的 Chat、智能体跟进和定时任务都落在绑定的机器；持有者停止后另一台接手且任务不轮空；缺能力的 Backend 不领 tools 为空的工作。
  5. Multica 和 Rook 正式环境都发布后，重跑 RK-24（tools 为空对比 ['*']）和定时任务的 SSO 检查。
未验证和风险

30 秒租约和 5 秒续约沿用现有 Run 租约的参数，没有线上实测。同一个 owner 在一台机器上能复用多少热状态，没有量过，绑定的收益是推断。新 owner 由第一个领到的机器绑定，不做负载均衡；现在每个应用只有一个副本，影响不大。发布 Rook 正式环境需要单独确认，在它升级之前，tools 为空的限制在线上仍然不可靠。
