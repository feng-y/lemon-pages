背景：三个事实决定准入

服务端把 Runtime 的可执行性拆成三个独立事实。修复都建立在这套模型上。

就绪 readiness启动检查快照每次检查
放开 enablement加密的 runtime-enablement 文档，revision CAS管理员在「启动依赖」保存

新建 Session、发送消息和入队走同一个判定，顺序固定。

顺序条件HTTP错误码

已接受的 requestId 重放不受之后的关闭影响。Session 创建重放返回原 Session，发送和自动化投递重放先命中原 Run。

修复一：fork 绕过准入

fork 是唯一一条不经过准入就创建 Session 的写路径。

改前，ConfigurationService.forkSession 直接创建新 Session，只校验原生 Session id 一致。Runtime 关闭时 fork 请求返回 201，新 Session 已经落库，用户下一次发送才收到 runtime_not_open。

改后，ChatManager.fork 在读到 fork 源之后、prepareFork 之前调用 requireRuntimeAccess。forkSession 在数据库事务内再调一次。未放开时请求返回 409，不生成新 Session，也不写原生 context 文件。

同一 requestId 的重放仍然先返回原 fork。priorFork 在两次校验之前执行，关闭不影响已完成的 fork。

测试在 tests/runtime-admission.test.ts。关闭 Pi 后调用 forkSession，断言返回 409 runtime_not_open，再重新放开。

修复二：系统 skill 目录不参与 Pi 就绪

检查表里能看到失败，就绪聚合却没有读它。

启动检查会产出「系统 skill 目录」一项。共享目录配置之后，inspectSkillAncestors 通过记 passed，抛错记 failed。

就绪聚合只读 runtimeChecks 列出的检查。system-directory 不在这张表里，失败只显示在检查明细，Pi 仍然聚合为 ready，新 Run 仍被放行。这是一处 fail-open。

改后 runtimeChecks.pi 加入 system-directory。目录失败时 Pi 不就绪，准入返回 503 startup_dependencies_unavailable。

Runtime聚合的检查
Pipersistence、system-directory、dw-cli、clawsec-bundle、system-skills、pi-cli
Claude Codepersistence、dw-cli、native-system-skills、claude-code-cli

只挂 Pi，因为 Pi 从共享目录发现系统 skill。Claude Code 和 Codex 用各自的原生系统 skill 目录，由 native-system-skills 覆盖，后者已经要求系统 skill 与 marketplace 都可用。

目录未配置时检查不产出，聚合里没有这一项，也就不会拦截。未探测不拦截是既定策略，这次没有改。

测试在 tests/startup-dependencies.test.ts。一条 system-directory 失败加一条 pi-cli 通过，断言 Pi 是 not_ready。

修复三：关闭的 Runtime 显示「未检查」

页面说明与页面内容在说两件事。

关闭或未接入执行器的 Runtime 不做探测。快照给这类 Runtime 补一条 unknown 的 CLI 检查，checkedReadiness 把非 passed 一律记成 not_ready，那一行就显示「未就绪」。页面说明写的是「未放开或未接入的 Runtime 不做探测，显示为未检查」。

矛盾点

同一行为什么显示未就绪，页面说明却说未检查。管理员看到「未就绪」会去找启动依赖的问题，实际原因只是没放开。

改后标签从事实推导，不再从聚合状态直接取。

未放开或执行器未接入未检查
就绪 ready已就绪
未就绪 not_ready未就绪
未探测 unknown未检查

准入不变。关闭的 Runtime 在判断就绪之前已经被 runtime_not_open 拦住，标签只是显示层。测试在 tests/web-startup-dependencies.test.ts，现在断言 1 个已就绪、1 个未就绪、1 个未检查。

状态机：五个状态与准入结果

三个事实的组合只有五种结果。把每种组合和它的转换写成 TLA+ 模型，再用 TLC 检查规则。

模型的状态由三项事实组成，管理页只显示合并后的结果。未放开的 Runtime 不做探测，页面显示「未检查」。放开了但执行器没接入，也显示「未检查」。放开了、执行器接入了，才按检查结果显示「未检查」「未就绪」或「已就绪」。

收敛：一处判定、一张名字表、一套术语

三件小事，都是为了下次改一处不会再漏另一处。

  • 准入判定收敛到 ConfigurationService.requireRuntimeAccess。Session 创建、发送与入队回调、fork、测试共用同一个方法。之前 server 和测试各自复制了一段判定。
  • 依赖检查名收敛到一张表 dependencyCheckNames。生产检查和就绪映射都读这张表。之前名字散在两处，改一处会让检查从就绪里静默消失，修复二就是这类问题。
  • 管理开关统一叫「放开」。模型选择器、Chat 提示、启动依赖页的开关、按钮和冲突提示全部改。两个地方保留「开放」：部署范围的文案，以及旧的 SkillDependencies 视图，那里的 enabled 是部署开关，不是管理员放开。
  • 删除 web/main.tsx 里只作兜底的 Runtime 标签表。运行时数据已经带 label。
