Rook Runtime 状态机评估

Pi、Claude Code、Codex 三个 Runtime 和它们之上的 Chat Turn 生命周期，对照 dsh、t3code、Orca。代码基线是 main c2163db 加 MR !243（6ed9642）。4 个 fable agent 只读评估，Claude 汇总并抽查。

TL;DR

三个 Runtime 的常驻方式已经和 t3code、Orca 一致。Claude Code 常驻一个 SDK query。Codex 常驻一个 app-server。生产的 Pi 走进程内 SDK。所以「每个 Turn 都重启进程」不是瓶颈。实测 Codex 退役后重启只多 0.3–0.4 s。

稳定性的主要缺口有四个。第一，删除 Session 的通知只到达 Pi 的 worker。第二，Codex 和 Claude Code 启动和握手没有期限，最坏要等 60 分钟的 Turn 总期限。第三，Claude Code 没有无响应看门狗。第四，Pi 的 bash 没有默认超时。这四个改动都不大。

效率的主要成本有三处。每个 Turn 都整文件传一遍 checkpoint，Pi 的 15 MB session 每个 Turn 约多花 0.6 s。RunEvent 每批要 12 条 SQL。Turn 结束后，Queue 最多空等 1 s 才派发下一条。

有一件事需要你拍板。失败或 Stop 的 Turn 做过的事，目前三个 Runtime 都不写进原生 context。t3code 和 Orca 都保留。

需要你拍板：失败或 Stop 的 Turn 要不要进入原生 context

现在三个 Runtime 的做法一致：失败或 Stop 的 Turn 不进入原生 context。Codex 退役进程后从 MySQL 恢复。Claude Code 有测试断言这一点（tests/claude-code.test.ts:392）。Pi 删掉本地 checkpoint。finishRun 只在 running 状态下保存。

结果是用户在界面上看得到这个 Turn 的回复和工具结果，模型在下一个 Turn 却不知道。比如 Stop 前已经改了文件，下一个 Turn 模型会以为文件没改。t3code 和 Orca 都保留这部分 context。

Claude 的建议

Stop 的 Turn 保留 context，因为 Stop 是用户主动打断，已完成的 Step 是事实。这样 S7 自然解决，Codex 也能少一次退役。Provider 报错的失败 Turn 维持现状，因为不完整的工具调用写进 context 风险更大。这个决定三个 Runtime 一起改，改动落在 Chat 公共层和三个 adapter 的退役条件上。

0. 结论

公共层的正确性设计是扎实的。租约、提交栅栏、supervisor 按租约杀进程，这三层让「running 但没有 owner」的 Run 最多存活约 30 秒。我没有找到会永久卡在 running 的主路径。

问题集中在四处：

  1. 删除 Session 时，Claude Code 和 Codex 的 worker 不会被停止。根因是一行 Object.assign（G1，读码）。
  2. 每批 RunEvent 的落库要 12 条 SQL，而整个 Rook Backend 只有 8 条 MySQL 连接（G2，实测 + 读码）。
  3. 空闲 worker 只按数量回收（每个 Runtime 4 个），没有按时间回收，也没有按执行实例总量回收（G3，读码）。
  4. Stop 赢了终态竞争时，Claude Code 和 Codex 的回复落库，checkpoint 不落库（G4，读码 + 实测状态）。

1.4 Stop 路径

  1. 浏览器调用 POST …/runs/<runId>/stop（chat/api.ts:237-239）。
  2. 收到请求的 Rook Backend 把 Run 从 running 改成 stopping（store.ts:682）。
  3. 这个 Rook Backend 持有 ActiveRun 时，立刻触发 abort（manager.ts:678）。
  4. 这个 Rook Backend 不持有时，持有者在下一次每秒轮询里读到 stopping 再触发 abort（manager.ts:759）。最坏延迟是 1 秒加上一轮 maintain 的耗时。
  5. abort 让 Rook Backend 向 worker 发 cancel，并启动 15 秒的取消期限（isolated.ts:376-385）。
  6. worker 触发自己的 AbortController（native-worker.ts:197-200）。之后由各 Runtime 适配器中断模型和工具。
  7. worker 回报结果。Rook Backend 让 supervisor 执行 clean，杀掉常驻进程之外的全部后代（isolated.ts:541-546）。
  8. Rook Backend 调用 finishRun。stopping 加任何非终态结果都落成 stopped（store.ts:724-725）。
  9. 15 秒内没有结果时，Rook Backend 杀掉 worker 和 supervisor，Run 落成 stopped，错误码 execution_cancel_timeout（manager.ts:558-560）。

1.6 空闲回收

  • 三个 Runtime 各有一个 isolatedExecutor，各有自己的 workers、live、idle 三张表（isolated.ts:89-93、isolated.ts:191-193）。
  • Turn 正常结束后，worker 进入 idle。idle 超过 maxIdleWorkers 时，Rook Backend 停掉最早进入的那个（isolated.ts:580-587）。默认值是 4（capacity.ts:6）。
  • 所以一个执行实例最多保留 12 个空闲 worker，每个 Runtime 4 个。
  • 没有按时间的回收。一个空闲 worker 只要没被挤出去，就一直活到 Rook Backend 退出。
  • Pi 的 worker 被回收后，下一 Turn 冷启动，并用本地文件或 MySQL checkpoint 恢复（isolated.ts:263-269）。
  • 空闲 worker 在 Turn 之间发来任何 IPC 消息都会被停掉（isolated.ts:146）。

重启恢复 不等租约过期。重启时检查记录的进程是否还活着。有证据证明 owner 已死才标 interrupted，否则标 unverifiable recovery/structured-agent-session-restart-reconcile.ts:106-120、termination/structured-agent-session-stale-turn-verdict.ts:31-60
空闲回收 脱离应用的 Codex relay 按 chat 空闲规则停止，24 小时硬上限，从未被认领的 60 秒后停 daemon/provider-relay/provider-relay-detached-cap.ts:17-19

与 Rook 的对照：

  • 租约参数几乎一样（Orca 30 秒 / 10 秒，Rook 30 秒 / 5 秒）。
  • Orca 的删除顺序是「先停进程，再删记录」。Rook 是「先删记录，再 forget」，而且 forget 只到 Pi（G1）。
  • Orca 的事件背压是高低水位，agent 在水位内不被阻塞。Rook 是每批停等（G2）。
  • Orca 的 Stop 总是连进程一起结束。Rook 的 Stop 保留 worker 和常驻进程，只在取消超时后才杀。Rook 的做法对下一 Turn 更快，前提是适配器的中断可靠。
  • Orca 靠 pid 记录文件在下次启动时清孤儿。Rook 靠 supervisor 的 PR_SET_PDEATHSIG 加 subreaper，当场清理，不需要启动扫描。Rook 的做法更强，只有 supervisor 自己被 SIGKILL 这一种双重故障会漏。

3. 差距，按影响排序

G1. 删除 Session 时，Claude Code 和 Codex 的 worker 不退出

影响：稳定性，高。这就是已知问题「已删除 Session 的 worker 和 app-server 不退出」。

证据（读码）：

  • 删除接口调用 chat.forgetSession（chat/api.ts:199-203），它调用 this.execute.forget（manager.ts:682-685）。
  • isolatedChatExecutor 用 Object.assign(execute, executors.pi, { supportsRuntime, supportsScheduleTools, close }) 组装执行器（isolated.ts:101-105）。
  • 第三个参数只覆盖了 supportsRuntime、supportsScheduleTools、close。forget 没有被覆盖，所以它是 executors.pi.forget。
  • executors.pi.forget 只查 Pi 执行器自己的 workers 表（isolated.ts:638-644）。Claude Code 和 Codex 的 worker 在另外两张表里，查不到就直接返回。
  • tests/pi-persistent.test.ts:347,388 只覆盖了 Pi 的 forget。

还有两个相邻的洞（读码）：

  • forgetSession 只在收到 DELETE 请求的那个 Rook Backend 上执行。Session 的 worker 在另一个执行实例上时，没有任何机制通知它。
  • 归档 Session 不调用 forgetSession（chat/api.ts:196、store.ts:335）。

这些 worker 不会无限增长。它们留在 idle 表里，等同一个 Runtime 出现第 5 个空闲 worker 时被挤掉。所以现象是「低流量时一直不退出」，上限是每个 Runtime 4 个。

改动：

  1. 在 isolatedChatExecutor 的第三个参数里加 forget，对三个执行器都调用一次。约 3 行。
  2. 补一个测试：对 { runtime: 'claude-code' } 的执行器跑一个 Turn，forget 之后断言 worker 的 exited 已完成。
  3. 跨执行实例的情况不需要新通道。G3 的按时间回收会在几分钟内收掉它。

成本与风险：成本很低。forget 对正在跑 Turn 的 worker 也会 stop()，但 deleteSession 已经要求 Session 空闲（store.ts:364），所以不会误杀。

G2. RunEvent 落库：每批 12 条 SQL，全进程 8 条连接，SSE 再用轮询读回来

影响：效率，高；高并发下也影响稳定性。

证据：

  • 实测（本机 MySQL 8.0.46，Unix socket，/tmp/rook-sm-scripts/db.mjs，用 SHOW GLOBAL STATUS LIKE 'Questions' 计数）：

    操作 SQL 条数 单次耗时
    appendEvents（1 个事件） 12 3.6 ms
    noteTool 开始加结束一对 14 3.4 ms
    beginRun 13 9.3 ms
    refreshLease 6 1.2 ms
    runState（每秒轮询） 1 0.28 ms
    runEvents（SSE 空轮询） 2 0.55 ms
    recoverExpired（空扫描） 2 0.41 ms

  • 实测：appendEvents 的 p50 在 1、8、20 个并发 Run 下分别是 2.7、8.8、19.3 ms。总吞吐从 357 次每秒升到 1006 次每秒就不再线性。瓶颈是 8 条连接。

  • 这些数字的下限来自本机 socket，单条 SQL 往返约 0.3 ms。线上经网络访问 RDS，往返更长。按 1 ms 估算，一次 appendEvents 约 12 ms 以上（推测，未在线上测）。

  • 读码：12 条 SQL 的构成是：事务外 ownedRun 一次；SET autocommit=0；Session 行锁；Run 行锁；租约行锁；查最后一个 chunk_index；INSERT；提交栅栏；恢复 wait_timeout（store.ts:645-675、store.ts:220-256）。其中 ownedRun 每次都经 run() 把 prompt 正文读一遍（store.ts:116、store.ts:139-142），事务内外各一次。

  • 读码：worker 发一批事件后必须等 events_saved 才能发下一批（native-worker.ts:128、isolated.ts:476-496）。这是停等式的背压。落库慢会直接拖慢 worker 读 Runtime 输出的速度。

  • 读码：连接池上限是 8，全进程共用（database.ts:5）。活动 Run 上限是 20（capacity.ts:2）。

  • 读码：SSE 不是推送。每个订阅者每 200 毫秒查一次库（chat/api.ts:303、chat/api.ts:306），每次 2 条 SQL。一个订阅者空转时是每秒 10 条 SQL。事件明明刚从同一个进程写进去。

  • 读码：每个活动 Run 每秒还有一次 runState 和一次 controls.claim（至少 1 条读），每 5 秒一次 refreshLease（6 条）（manager.ts:741-763、controls.ts:50-54）。

  • 读码：Pi 的每次工具调用有两次 noteTool 事务，工具要等「开始」落库后才执行（manager.ts:488-495、isolated.ts:525-535）。

粗算：20 个活动 Turn，每个有 1 个浏览器订阅，Pi 每 100 毫秒一批事件。写入是 20 × 10 × 12 = 2400 条每秒，SSE 轮询是 20 × 5 × 2 = 200 条每秒，全部挤在 8 条连接上（推测，由上面的实测单价乘出来）。

改动，按收益排序：

  1. appendEvents 瘦身。mutateRun 改用不读正文的 Run 行查询；事务外的预读删掉，session_id 由调用方传入；序号由 Rook Backend 在内存里按 Run 递增，去掉查 chunk_index 的那一条（唯一键 uk_run_content 仍会兜住重复）。预计 12 条降到 6 到 7 条。
  2. SSE 改成进程内通知。appendEvents 和 finishRun 提交后，Rook Backend 按 runId 触发一个 EventEmitter；streamEvents 等通知或 2 秒超时，再查库。查库逻辑和游标不变，所以跨执行实例的订阅仍然靠超时轮询正确工作。
  3. 连接池从 8 调到与 activeRuns 匹配的值，并做成环境变量。先确认 RDS 侧的连接上限。
  4. 落库节奏向 dsh 的 200 毫秒靠拢，或者在上一批未确认时让 worker 继续合并 text_delta。Pi 路径已经在合并（native.ts:425）；Claude Code 和 Codex 的节奏请看另外两份报告。

成本与风险：第 1 项和第 2 项各是半天量级，都有现成测试覆盖（tests/chat-store.test.ts、tests/chat-events.test.ts）。第 1 项动的是带栅栏的事务，必须保留三把行锁的顺序和提交栅栏，否则 1.9 节的互斥不再成立。第 3 项要过 RDS 评审。

G3. 空闲回收只看数量，不看时间，也不看总量

影响：效率与稳定性，中高。

证据：

  • 读码：回收只有「每个 Runtime 的 idle 超过 4 个就停最早的」这一条规则（isolated.ts:580-587）。

  • 读码：三个 Runtime 各算各的，一个执行实例最多 12 个空闲 worker。每个 Claude Code 或 Codex 的 worker 还带一个常驻进程。

  • 读码：没有空闲时长上限。用户下班后，他的 worker 和常驻进程一直占着内存。

  • 读码：反过来，同一 Runtime 有 5 个以上 Session 轮流活跃时，每个 Turn 都可能冷启动。

  • 实测冷启动成本（本机，3 次取值）：

    环节 耗时
    python3 -I 启动 supervisor 23 到 30 ms
    setpriv 加 node 空启动 44 到 55 ms
    node 加载 dist/server/chat/native.js（Claude Code、Codex 的 worker 也要加载它） 592 到 617 ms
    node 加载 pi-sdk-runtime.js 并构造 PiSdkRuntime（Pi 的 worker） 1170 到 1201 ms

    这些数字只含进程启动和模块加载，不含 checkpoint 恢复、skill 快照和 Runtime CLI 自己的启动。所以 Pi 的 worker 冷启动下限约 1.2 秒，另两个约 0.7 秒再加 CLI 启动。

改动：

  1. 加一个空闲时长上限。worker 进入 idle 时记时间戳；ChatManager.poll 已经每秒跑一次，在执行器上加一个 reap(now)，停掉超时的。建议默认 15 分钟，做成环境变量。
  2. 把 idle 表提到 isolatedChatExecutor 一层，三个 Runtime 共用一个上限。默认值可以调高到 8 到 12。
  3. 数量上限和时长上限都保留。数量管内存峰值，时长管闲置。

成本与风险：约 30 行加测试。Pi 的 worker 被回收后要从本地文件或 MySQL 恢复 context，这条路径已经存在并有测试（tests/pi-persistent.test.ts）。Claude Code 和 Codex 被回收后的冷启动由各自的适配器负责，沿用现有的回收和恢复即可。

G4. Stop 赢了终态竞争时，回复落库但 checkpoint 不落库（Claude Code、Codex）

影响：稳定性，中。表现是「界面上有这条回复，下一 Turn 的模型不记得它」。

证据：

  • 读码：finishRun 只在 current.state === 'running' 时保存 checkpoint（store.ts:714-720）。stopping 时跳过，但回复文本照常写入（store.ts:721-722），终态是 stopped。
  • 实测：requestStop 之后 finishRun({ state: 'succeeded', response: 'full answer' }) 返回 stopped（探针脚本最后一行）。
  • 读码：manager.ts:547 对 Claude Code 和 Codex 要求成功结果必须带 checkpoint，所以走到这里时 checkpoint 是齐的，只是被丢了。
  • 推测：常驻进程此时的 context 比 MySQL 新一个 Turn。下一 Turn 的 contextSha 对不上，适配器会关掉常驻进程并从旧 checkpoint 冷启动。这一步的实际行为请以另外两份报告为准。

这个窗口很窄：Stop 必须落在 Runtime 已经完成、finishRun 还没提交之间。

改动：stopping 且 Runtime 结果是 succeeded、工具计数能对上时，照常保存 checkpoint，终态仍写 stopped。改动在 store.ts:714 的条件上。

成本与风险：一行条件加一个测试。风险是 Stop 的语义：用户按了 Stop，但这一 Turn 的内容进了 context。回复文本本来就已经展示给用户，两者一致比不一致好。

G5. 准入在一个执行实例内全局串行

影响：效率，中；有连带的稳定性风险。

证据（读码）：

  • manager.ts:298 把所有用户的 accept 串在一条链上。
  • accept 里有多次 MySQL 往返，还有 configuration.resolve、gitRuntimeAccess、sessionSkills.execution（manager.ts:339-386）。
  • sessionSkills.execution 会做 skill 绑定或 Pi skill 发现（session-skills.ts:28-40）。它慢的时候，其他用户的发送全部排在后面。它实际多慢，我没有量。
  • 等待超过 8 个时，直接发送转 Queue，其余路径报 chat_run_overloaded（manager.ts:292-297）。
  • Queue 派发每批 4 个 Session 并发调用 send，同样挤进这条串行链（manager.ts:177-178）。

我没有实测准入耗时。beginRun 单独是 9.3 ms、13 条 SQL（实测）；整个 accept 的耗时是推测：几十到几百毫秒。

改动：把串行的粒度从「执行实例」改成「Session」。容量检查（manager.ts:360-367）需要在同步段里完成「检查并占位」，占位失败或后续失败时释放。跨 Session 的正确性已经由 beginRun 的行锁保证。

成本与风险：中。容量计数从「读 this.active」变成「预占」，要处理每一条失败路径的释放。建议先加一行日志量出准入排队时长，再决定做不做。现在只有 Queue 的 chat_queue_admitted wait_ms（manager.ts:233）。

G6. Queue 的全局索引文档是所有用户共用的一把锁

影响：效率，中低。

证据（读码）：

  • 每个执行实例每秒读一次索引文档，带 FOR UPDATE（queue.ts:33，第 6 个参数是锁标志，见 configuration-store.ts:25-28）。
  • 任何 Session 的 Queue 在空与非空之间切换时，都要锁并重写这份文档（queue.ts:60-69）。
  • 派发时对每个有 Queue 的 Session 每秒做一次 snapshot，它锁 Session 行（queue.ts:40-42、queue.ts:73-78）。这把锁和 appendEvents 的 Session 行锁是同一把。
  • 索引上限 512 个 Session，超出报 chat_queue_overloaded（queue.ts:65）。

Queue 里有消息的 Session 通常正在跑 Turn。所以派发轮询每秒都会和这个 Turn 的事件落库抢一次 Session 行锁。

改动：

  1. targets() 改成不加锁的读。它只是候选列表，后面每一步都有自己的校验。
  2. dispatchQueue 先用内存里的 this.active 过滤掉本执行实例正在跑的 Session，再做 snapshot。插话的收尾逻辑（manager.ts:186-195）需要 snapshot，只对带 steering 标记的 Session 保留。
  3. Turn 结束时调用 wakeQueue()，去掉 0 到 1 秒的固定延迟。

成本与风险：低。第 2 项要小心不要漏掉「Run 已结束但插话回执未结清」的 Session。

G7. MySQL 抖动 30 秒会中断一个执行实例上的全部 Turn

影响：稳定性，中；发生频率是推测：低。

证据（读码）：租约 30 秒，续期每 5 秒（store.ts:27、manager.ts:757）。续期和 inspectLease 都失败时，本地期限不变，到期即 interrupt（manager.ts:745-749、manager.ts:715-719）。同一时刻 supervisor 也会杀掉 worker。

这是租约设计的必然代价，方向是对的：宁可中断，也不要两个 owner。可调的只有时长。

改动：把 CHAT_LEASE_MS 调到 60 到 90 秒，续期间隔不变。代价是 owner 真死时，Run 多等 30 到 60 秒才变 interrupted。执行实例心跳的 15 秒失效不受影响。

成本与风险：一个常量。上线前要确认 RDS 主备切换的典型时长，选一个盖得住的值。

G8. 公共层没有「活着但不出声」的检测

影响：稳定性，中低。

证据（读码）：公共层对 worker 只有 60 分钟总期限（isolated.ts:375）。worker 进程活着、IPC 连着、但一直不发事件时，Run 保持 running，租约照常续期。各 Runtime 自己的超时（Pi 的 HTTP 空闲、Codex 的 180 秒看门狗）在 worker 内部。

worker 的事件循环卡死时，worker 内部的超时也不会触发。此时只有 60 分钟总期限和用户 Stop（15 秒后强杀）能收场。

改动：worker 每 10 到 15 秒经 IPC 发一个心跳帧。Rook Backend 在 isolated.ts 里记最后一次收到任何帧的时间，超过 60 秒没有帧就按 execution_worker_unresponsive 停掉 worker。execution_worker_unresponsive 是我新起的错误码。它只判断 worker 进程是否响应，不判断模型是否在输出，所以不会和各 Runtime 的空闲超时打架。

成本与风险：约 20 行。worker 在做同步的大文件读写时可能误报，阈值要留足。

G9. 较小的事项

每项只记一行，不展开。

  • manager.ts:557 把非白名单前缀的错误码压成 runtime_execution_failed。把 ChatError 的 code 写进 errorDetail 即可保留信息。读码。
  • Turn 成功但 finishRun 失败时，最终回复丢失（1.5 节）。可以在 catch 里对 succeeded 的结果重试一次原结果，而不是直接写失败态。读码。
  • active_run_id 指向不存在的 Run 行时 Session 永久 session_busy（1.8 节）。recoverSession 可以在这种情况下直接清空 active_run_id。读码；出现概率是推测：很低。
  • Queue 因满载而等待时没有上限和告警（1.8 节）。读码。
  • recoverExpired 把过期的 Run 一律写成 interrupted，不区分 Run 是否已经交给 Runtime。t3code 把没开始的 Run 放回队列（2.2 节）。Rook 要做到这一点需要先在 Run 上记录「已交给 Runtime」，收益是推测：只影响执行实例重启瞬间刚准入的 Turn。
  • 16 MB 以内的 Pi context 每次 checkpoint 都整份经 IPC 传给 Rook Backend（isolated.ts:400-410）。我没有读 context.ts 的写入方式，是否整份重写 MySQL 请看 Pi 适配器报告。

  • 术语：Session、Turn、Step 按 CONTEXT.md。讨论后端实现时保留 Run 和 runId。resident 指 CodexResident，即一个 Session 常驻的 codex app-server 进程。
  • 证据标签：实测 表示我跑了代码并读到了数字。读码 表示我只读了源码。猜测 表示没有证据支撑。

0. 结论

  1. 「失败 Turn 后退役 resident 的冷启动成本高」这个前提不成立。实测：Rook 适配器复用 resident 的 Turn 用 58 到 76 ms，退役后下一个 Turn 用 348 到 440 ms，差约 0.3 到 0.4 秒。thread/resume 在 36 MB rollout 上用 183 到 200 ms。一次真实模型 Turn 是几秒到几分钟。退役策略不值得为了效率去改。
  2. 最大的稳定性缺口是握手阶段没有期限。实测：app-server 不回 initialize 时，Rook 的静默看门狗不生效，Turn 一直等到总期限。生产的总期限是 60 分钟。
  3. 第二个缺口是 Rook 丢掉了 codexErrorInfo。所有失败 Turn 都报 native_codex_turn_failed，自动化任务的重试集合不含这个码，所以 Codex 的过载和限流不会被重试。
  4. t3code 在失败 Turn 后并不退役 app-server。codex-app-server.ts:80 的注释「Lifecycle follows t3code: any failed Turn retires the whole process」与 t3code 当前代码不一致（读码）。

3. 差距，按对稳定性和效率的影响排序

G1. 握手和 RPC 请求没有期限（稳定性，高）

  • 证据：实测。mute.mts 让 app-server 不回 initialize。500 ms 的静默看门狗没有触发，Turn 在 4021 ms 的总期限才结束。原因是 turn.heard() 第一次调用在 turn/start 的回复里（codex-app-server.ts:327），而 request() 自己没有期限（:173-193）。生产的总期限是 60 分钟（process.ts:5）。app-server 在 initialize、model/list、thread/resume 或 turn/start 任何一步卡住，用户都要等 60 分钟或手动 Stop。
  • 参考：t3code 是 30 秒和 2 分钟，超时退役进程。Orca 是 30 秒。
  • 改法：在 run() 里创建 turn 之后立刻调一次 turn.heard()，让 180 秒的静默计时覆盖握手阶段。握手阶段 turn.id 为空，interrupt() 会直接关闭进程（:313）。更好的做法是给握手单独一个 30 秒期限，并报 native_runtime_unavailable，不报 native_model_timeout。
  • 归属：Codex 适配器。「每个 RPC 请求都有期限」这条规则也适用于 claude-code.ts 的 resident，我没有核对那边。
  • 成本和风险：约 5 行加一个假 app-server 的测试。风险低。实测 thread/resume 在 36.7 MB 上只用 0.2 秒，30 秒不会误杀。

G2. 失败码不区分 codexErrorInfo（稳定性，高，主要影响自动化任务）

  • 证据：读码 codex-app-server.ts:267-268、:280-283 只取 message。所有失败都是 native_codex_turn_failed（:353）。自动化任务的可重试集合是 native_model_rate_limited、native_model_unavailable、native_model_timeout（src/automation/service.ts:123）。所以 Codex 的过载、限流、5xx 耗尽重试之后，自动化任务不会重投。实测 过载时 codexErrorInfo 是字符串 serverOverloaded，重连时是 {responseStreamDisconnected:{httpStatusCode:503}}。
  • 参考：t3code 和 Orca 都按 codexErrorInfo 归类。
  • 改法：适配器在 turn/completed 的 error 和 willRetry: false 的 error 里读 codexErrorInfo，用一张表映射到 Rook 已有的失败码。serverOverloaded、flexUnavailable、policyCapacityUnavailable 映射到 native_model_unavailable。usageLimitExceeded、rateLimitExceeded、或 httpStatusCode 为 429 映射到 native_model_rate_limited。responseTooManyFailedAttempts、responseStreamDisconnected、httpConnectionFailed 带 5xx 时映射到 native_model_unavailable。其他保持 native_codex_turn_failed。
  • 归属：失败码词表属于 Rook Backend，三种 Runtime 共用。映射表属于 Codex 适配器。
  • 成本和风险：约 15 行加测试。风险低。要确认前端 web/main.tsx 对这两个码的文案适用于 Codex。
  • 不建议现在抄 t3code 的过载重发。重发要求失败后保留进程和 thread，这依赖 G6。映射完成后，自动化任务已经能在 Run 层重投。

G3. willRetry: true 映射到 auto_retry_start（已知后续项，这里细化）

  • 证据：实测 通知的形状见 1.6。读码 前端已经有 auto_retry_start {attempt, maxAttempts, delayMs} 和 auto_retry_end {attempt, success}（src/chat/events.ts:15-16、:58-59，web/run-events.ts:139-143）。校验要求 attempt >= 1、maxAttempts >= attempt、delayMs 是非负整数。
  • 改法：
    1. runCodexAppServer 现在只有 onTurnStarted，没有事件回调。先加一个 onEvents，由 native.ts 接到已有的 options.onEvents。
    2. 适配器用 t3code 的正则 (\d+)\s*/\s*(\d+) 从 error.message 取 attempt 和 maxAttempts。取不到时 attempt 用上一次加一，maxAttempts 用 5。Codex 不给退避时长，delayMs 填 0。
    3. 之后第一条 item/started 或 item 增量通知发 auto_retry_end {success: true}。turn/completed 为 failed 时发 success: false。
    4. 不要把 additionalDetails 发给前端。实测 它含 relay 的 loopback URL。
  • 归属：事件类型在 src/chat/events.ts，三种 Runtime 共用。转换在 Codex 适配器。
  • 成本和风险：约 30 行加一个测试场景。风险低。
  • 可选：t3code 的 10 分钟重试预算。Rook 现在最坏情况是 6 次请求乘 60 秒响应头期限，或 6 次乘 120 秒流空闲，即 6 到 12 分钟，量级已经相当。不建议再加一层预算。

G4. 不知道 resident 的复用命中率，空闲 worker 没有时限（效率和资源，中）

  • 证据：读码 native.ts:358 丢掉了 reused，Run 记录里没有它。空闲 worker 上限默认 4（capacity.ts:6），按每个 Backend 实例、每种 Runtime 计。超过上限时停掉最早空闲的 worker（isolated.ts:580-586）。没有空闲时限。实测 一个空闲 app-server 的 RSS 约 110 MB。
  • 影响：同时有 5 个以上 Session 交替使用 Codex 时，resident 会被挤掉，每个 Turn 都要重新启动 worker 和 app-server。生产的命中率是多少，是猜测，我没有数据。反过来，少于 4 个 Session 时，空闲的 app-server 会一直占着 110 MB，直到 Backend 实例退出。
  • 改法：先记录再调参。
    1. 把 reused 和未命中的原因（进程已死、launchKey 变了、contextSha 不等、thread 不等、worker 被回收）写进 Run 的诊断字段。
    2. 有数据后再决定是否调大 ROOK_CHAT_MAX_IDLE_WORKERS，并给空闲 worker 加时限。Orca 的值是 30 分钟。
  • 归属：isolated.ts 的 worker 池，三种 Runtime 共用。
  • 成本和风险：记录约 10 行。空闲时限约 15 行。风险低。
  • 顺带解决已知后续项「已删除 Session 的 worker 和 app-server 不退出」。读码 forget 只作用于收到 DELETE 请求的那个 Backend 实例（isolated.ts:638-644）。如果 worker 在另一个实例上，没有人通知它。这个原因是猜测，我没有核对生产是否多实例。空闲时限不需要跨实例通知就能回收这些 worker。

G5. 复用 resident 时仍然每个 Turn 往返一次完整 rollout（效率，中，未测）

  • 证据：读码。ChatManager 每个 Turn 从 MySQL 读出完整 context（manager.ts:445-450）。executeNative 新建 CODEX_HOME 并写入 rollout（native.ts:177-193），复用时再删掉（:357）。contextSha 对全文算两次 sha256（native.ts:343、:353）。Turn 成功后 executeNative 再读出全文，经 IPC 交给 Backend 加密写回。rollout 上限是 16 MiB（src/chat/native-context-format.ts:5）。
  • 影响：每个 Turn 有两次与 rollout 等大的读写。本地文件部分很小，实测 复制 12 MB 的 CODEX_HOME 用 63 ms。MySQL 读取和解密的耗时我没有测，需要生产数据。
  • 改法：用 MySQL 的 NativeContextHead.sha256 和 resident.contextSha 比较，命中时不读正文，不建 CODEX_HOME。Pi 已经有 checkpoint.head 加 load() 的形状（isolated.ts:265-268）。现在 worker 协议拒绝 one-shot Runtime 带 checkpoint（native-worker.ts:88），要放开。
  • 归属：ChatManager 和 worker 协议，Claude Code 的 resident 同样受益。
  • 成本和风险：中等，改动跨过 worker 信任边界。先在 G4 的诊断里加上「context 加载耗时」，有数据再决定。

G6. 失败或 Stop 的 Turn 丢掉 context 并退役进程（语义差异，效率影响小）

  • 证据：实测 退役的代价只有 0.3 到 0.4 秒。实测 失败或中断后，同一个 app-server 可以正常跑下一个 Turn。读码 t3code 和 Orca 都保留失败或中断 Turn 的历史。Rook 回到上次成功的 checkpoint（codex-app-server.ts:461-465，isolated.ts:574）。
  • 真正的差别不在速度，在 context。用户 Stop 一个已经执行过命令的 Turn 之后再继续，Rook 的模型不知道这些命令执行过。前端文案「请确认已发起的操作，再继续会话」（web/main.tsx:148）把这个核对交给了用户。
  • 判断：不建议为了效率改退役策略。退役让「进程里的 thread」和「MySQL 的 checkpoint」始终一致，这个不变量很便宜也很稳。
  • 如果要对齐 t3code 的语义，改法是：收到干净的 turn/completed（interrupted 或 failed）时也保存 rollout，并保留 resident。这是 Rook Backend 的规则「哪些 Turn 终态保存原生 context」，三种 Runtime 要一起定。它还会碰到「存在未知工具结果时保留原有 checkpoint」这条规则。成本大，风险中到高。这是产品决定，需要用户拍板。
  • 无论是否改，codex-app-server.ts:80 的注释应该改掉。t3code 不在失败 Turn 后退役进程。

G7. 未知的服务端请求直接让 Turn 失败（稳定性，低到中）

  • 证据：读码 codex-app-server.ts:257。Rook 用 approvalPolicy: 'never'（:222），定时 MCP 用 default_tools_approval_mode="approve"（:150），所以审批请求不会出现。实测 普通 Turn 里没有服务端请求。可能出现的是用户安装的 skill 带来的 MCP elicitation，或模型调用 requestUserInput。生产上是否出现过，是猜测。可以查 native_codex_request_unsupported 的 Run 数量来确认。
  • 参考：t3code 回 -32601，Orca 回 -32000，Turn 继续。
  • 改法：对未知方法回 {id, error: {code: -32601, message: 'Method not found'}}，不关闭进程。Codex 收到错误后是否继续 Turn，我没有实测。
  • 归属：Codex 适配器。
  • 成本和风险：2 行。先查生产数据，没有出现过就只记 TODO。

G8. 不需要改的项

0. 先说结论

任务描述里的前提有一处已经过时。Rook 不是每个 Turn 新开进程。Rook 已经和 t3code、Orca 一样，每个 Session 保留一个 Agent SDK query()（CC:92-158）。所以「每个 Turn spawn 一次」不是差距。

真正的差距按影响排序如下，详见第 4 节。

  1. Rook 没有 Turn 级的无响应 watchdog。卡住的 Turn 要等 1 小时总期限。
  2. Rook 丢弃了 result 以外的所有帧。用户看不到重试，后端也分不清失败原因。
  3. 常驻进程复用时，Rook 仍然每个 Turn 把整份 checkpoint 从 MySQL 读出、经 IPC 送进 worker、落盘、再删除。
  4. Rook 只认「推入消息后的第一个 result」。Claude Code 自己发起的 Turn（后台任务结束后）会让下一个 Turn 拿错结果。
  5. 每个新 Session 多发一次起标题的模型请求，用的是主模型。

Stop 的处理三家一致：Stop 之后都关进程。这一项不用对齐。

4. 差距和建议

按对稳定性和效率的影响排序。「层」一栏写改动落在哪里：适配器指 src/runtime/claude-code.ts，Chat 层指与 Runtime 无关的 src/chat/。

G1. 没有无响应 watchdog 和启动期限（稳定性，高）

  • 证据（读码）：receive 只转发帧，不记时间（CC:189-194）。唯一的定时器是 60 分钟（CC:213）。system init 没有期限。
  • 证据（读码）：API_TIMEOUT_MS 和流空闲超时只管模型请求。MCP relay 挂住、进程死锁、Claude Code 连续重试，都落到 60 分钟。
  • 猜测：Claude Code 每次重试最多等 180 秒。重试次数的默认值我没有查到。api_retry 帧带 max_retries 字段（sdk.d.ts:3986），可以实测。
  • 参考：t3code 用 10 分钟，按「有请求在等」上弦，根帧重置，后台任务帧不重置。
  • 改动：在 ClaudeResident.run 里加一个定时器。推入消息时上弦。receive 收到根帧时重置。工具执行期间不计时，否则长时间的 Bash 会被误杀。到点后走现有的 interrupt() 路径，返回新代码 native_stalled。
  • 层：适配器。Codex 适配器可以用同一个常量。
  • 成本：小，约 30 行加一个测试。测试可以复用 tests/claude-code.test.ts:138 的假 Provider，让它不回响应头。
  • 风险：工具执行期间是否有帧到达，我没有实测。上线前要用 sleep 700 的 Bash 验证不会误杀。

G2. result 之外的帧全部丢弃（稳定性和可观测性，高）

  • 证据（读码）：适配器只在 result 时 resolve（CC:219）。Rook 对 Claude Code 只写 assistant_started 和 assistant_completed 两个事件（NAT:311-322）。
  • 后果（读码）：用户在整个 Turn 里看不到文本、工具 Step 和重试。一个正在重试的 Turn 和一个卡死的 Turn 在 Web 上没有区别。
  • 后果（读码）：includePartialMessages: true（CC:130）让 Claude Code 输出全部增量帧，适配器随后把它们丢掉。
  • 参考：t3code 和 Orca 都把 api_retry 显示给用户。
  • 改动分两步。第一步只接 api_retry：适配器把最近一次重试的 error_status 和次数经 onEvents 发出，失败时并入 errorDetail。第二步接文本增量和工具 Step，映射到 Pi 已经使用的 RuntimeEvent。
  • 层：帧的解析在适配器。事件类型和持久化在 Chat 层，沿用 Pi 的事件，Codex 也能接。
  • 成本：第一步小。第二步中等，要对齐 Web 的 Step 展示和事件落库节流（NAT:427 的 100 ms 批量）。
  • 风险：第二步让事件量上升。在第二步做完之前，可以把 includePartialMessages 关掉，省掉无用的帧解析。省多少我没有测。

G3. 复用常驻进程时仍然全量往返 checkpoint（效率，高）

  • 证据（读码）：Claude Code 的 worker 禁止传 checkpoint 头（WRK:88）。Rook Backend 每个 Turn 把整份 JSONL 作为 nativeContext 经 IPC 送进 worker（ISO:612）。
  • 证据（读码）：worker 对内容做凭据扫描、写到新建的 CLAUDE_CONFIG_DIR、算 sha256（NAT:177-203，NAT:379）。复用成立后 worker 再把这个目录删掉（NAT:382）。
  • 证据（读码）：Turn 成功后 worker 读整份 JSONL 送回，Rook Backend 加密写 MySQL（NAT:390-393）。JSONL 上限 16 MiB（src/chat/native-context-format.ts:5）。
  • 结论：常驻进程把 Claude Code 自身的开销降到几十毫秒（实测），但 Rook 每 Turn 的开销仍然和 JSONL 大小成正比。这部分耗时我没有实测，因为探测环境没有 MySQL。
  • 参考：Pi 的 persistent worker 已经只比较 checkpoint 头（ISO:263-267），内容按需加载（WRK:97-106）。
  • 改动：让 Claude Code 和 Codex 的 worker 走 Pi 的同一条路。Rook Backend 只发 checkpoint 头。常驻进程用头里的 sha256 和自己记下的 contextSha 比较。不相等时 worker 才发 checkpoint_required。
  • 层：Chat 层（isolated.ts、native-worker.ts、native.ts）。适配器不动。
  • 成本：中等。先做一次测量：在 executeNative 的 Claude Code 分支前后打点，看一个 5 MB 的 Session 每 Turn 花多少毫秒。数字小就不做。
  • 风险：复用判断从「内容相同」变成「头相同」。头里的 sha256 必须和保存时的内容一致，这一点 Pi 路径已经在依赖。

G4. result 按到达顺序归属（稳定性，中，未复现）

  • 证据（读码）：run() 把推入消息后的第一个 result 当作本 Turn 的结果（CC:217-220）。Turn 之外到达的帧被丢弃（CC:193）。
  • 风险（猜测）：Chat Run 用 bypassPermissions，模型可以启动后台 Bash 或后台子 agent。后台任务结束后 Claude Code 会自己发起一个 Turn。这个 Turn 的 result 如果在下一个用户 Turn 推入之后到达，Rook 会把它当成用户 Turn 的答案。我没有复现。
  • 参考：t3code 为这类 Turn 做了续接缓冲。Orca 给每条消息带 uuid，按 uuid 归属。
  • 改动（最小）：在适配器的 env 里设 CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1。这个变量名在 2.1.332 的二进制里存在（实测，strings）。它的实际效果我没有验证。
  • 改动（完整）：推入消息时带 uuid，只接受对应的 result。SDK 是否在 result 上回传这个 uuid，要先探测。
  • 层：适配器。
  • 成本：最小改动一行加一次探测。完整改动中等。
  • 风险：关掉后台任务会改变模型可用的能力。这是产品取舍，需要用户确认。

G5. 进程退出和启动失败没有原因（稳定性，中）

  • 证据（读码）：stderr 被丢弃（CC:138）。SDK 迭代器的异常被空 catch 吞掉（CC:153）。退出码和信号没有记录（CC:141-144）。
  • 后果：进程崩溃、被 OOM 杀死、resume 的会话文件不被接受、Provider 认证失败后退出，在 Run 上都是没有 errorDetail 的 native_incomplete。
  • 参考：Orca 把 No conversation found 分类为会话缺失，把非零退出和信号分开。t3code 做同样的分类。
  • 改动：保留 stderr 的最后 1 KB。记录退出码和信号。把迭代器异常的消息留下。三者经现有的 errorDetailText 去掉凭据后写入 errorDetail。新增代码 native_process_exited。No conversation found 映射到已有的 native_context_missing。
  • 层：适配器。errorDetail 的通道已经存在。
  • 成本：小。
  • 风险：stderr 可能带凭据或路径。必须走 errorDetailText 和 Rook Backend 的二次脱敏（ISO:536）。

G6. 每个新 Session 多一次主模型请求（效率，中，改动一行）

  • 证据（实测）：见第 1 节。请求用主模型和 effort: high。
  • 后果：真实 Provider 下，这是每个新 Session 一次额外的付费请求，并且和首个 Turn 的请求同时发出。Rook 不使用 Claude Code 生成的标题。
  • 改动：在 CC:117-119 的 env 里加 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC: '1'。
  • 层：适配器。
  • 成本：一行。现有测试里假 Provider 对旁路请求回 side（tests/claude-code.test.ts:343），改完后可以断言旁路请求数为 0。
  • 风险：这个变量还会关掉其他非必要流量。我只验证了标题请求消失和普通 Turn 仍然成功。MCP、skill、plugin 是否受影响没有测。

G7. 失败的 Turn 之后关进程（效率，低）

  • 证据（读码）：任何非 succeeded 的结果都会关掉常驻进程（CC:339-342）。t3code 和 Orca 在失败的 result 之后保留进程。
  • 证据（实测）：关进程约 0.6 秒，下一个 Turn 冷启动约 0.55–1.07 秒，再加 Rook 的 checkpoint 恢复。
  • Rook 关进程是有意的。失败和被停的 Turn 不进 checkpoint，测试断言了这一点（tests/claude-code.test.ts:392）。保留进程会让进程里的 context 比 MySQL 多一个 Turn。
  • 判断：不建议现在改。每次失败只省 1–2 秒，而要改的是「失败的 Turn 是否进入 context」这个 Chat 层的语义，三个 Runtime 都受影响。
  • 层：Chat 层的语义决定，适配器只是执行。

G8. Stop（已对齐，不用改）

  • 三家在 Stop 之后都关进程。Rook 的 10 秒 interrupt 宽限和 t3code 相同，Orca 是 3 秒。
  • 实测：流式文本期间 interrupt 到 result 只要 6–9 ms。10 秒宽限只在工具执行期间才可能用到。
  • 语义差异：Rook 丢掉被停的 Turn。t3code 和 Orca 的下一个 Turn 能看到被停的 Turn。这是产品选择，不是缺陷。要对齐就得在 Stop 时也存 checkpoint，归 Chat 层。

G9. 两个需要先量再定的数

  • 空闲常驻进程预算。默认只保留 4 个空闲 worker（src/chat/capacity.ts:6）。第 5 个 Session 的常驻进程会被停掉，回来时冷启动。实测一个常驻进程的 RSS 是 288–381 MB。按实例内存算一下能否把预算提高。Orca 用 30 分钟空闲时间回收，不用个数。这是部署配置，不是代码改动。
  • JSONL 的 16 MiB 上限。超过后 readPortableContext 抛 native_context_invalid（NAT:575）。实测 6 个最小的 Turn 写出 112 KB，155 个各 20 KB 回复的 Turn 写出 3.85 MB。猜测：工具用得多的长 Session 会碰到上限，之后这个 Session 的每个 Turn 都失败。建议先在 MySQL 里查现有 Claude Code Session 的 checkpoint 字节数分布。

2.2 Rook 已经对齐的地方

以下都是读代码的结论。

  • Rook 把 retry 和 compaction 做成 RunEvent。t3code 和 Orca 也是只展示不干预。
  • Rook 用 waitForIdle 判定 Turn 结束。t3code 和 Orca 用 agent_settled 加 get_state。语义相同。
  • Rook 的插话在 Step 边界生效。三家相同。
  • Rook 的 compaction 阈值、prune 预算、summary 指令直接抄 dsh。
  • Rook 没有“无活动看门狗”。三家也都没有。这一项不算差距。
  • Rook 的 Queue 每条消息开一个新 Run。这是 Rook Backend 统一 Run 语义的设计，不是差距。

3. 差距，按对稳定性和效率的影响排序

G1. checkpoint 是整文件复制，本地 JSONL 不是事实来源（3a 已计划）

  • 证据（读代码）：worker 每次 checkpoint 读整个 session 文件并整份经 IPC 发送（src/chat/native.ts:434-449, 468-497，src/chat/native-worker.ts:127）。超 16 MiB 时 checkpoint 静默跳过（src/chat/native.ts:491-493）。Stop 或失败时 Rook 删 active.checkpoint 并丢弃本地 context（src/chat/isolated.ts:574-575, 588-589）。
  • 证据（实测）：15 MB 文件一次 checkpoint 的 IPC 往返 240 ms，子进程发送 143 ms，Rook Backend 事件循环单次阻塞 ≥ 53 ms（只算 IPC 解析）。每个 Turn 的固定开销在 1 MB 时约 30 ms，在 15 MB 时约 0.6 s。明细见 4.1。
  • 对照：dsh、t3code、Orca 都把 append-only 日志当事实来源。dsh 在 LLM 请求前和工具批前强制 flush。
  • 改动：3a 落地时让 checkpoint 只发增量（上次已确认的字节偏移之后的行）。src/chat/context.ts:393-423 已经按 64 KiB 分片去重并校验前缀 sha，Rook Backend 侧存储不用改。
  • 层：Pi adapter（worker 侧）加 executor 的 context 帧。存储层属 Runtime 无关的 Chat 层，不动。
  • 成本和风险：中。风险在前缀校验失败时要退回整文件路径。3a 分支已在开发，这里只是补数据。
  • 收益：消除长 Session 的 O(文件大小) 开销，去掉 16 MiB 断崖。收益大小按实测数据推算，线上长 Session 的占比没有查，属推断。

G2. 冷启动贵，idle 预算只有 4

  • 证据（实测）：worker 冷启动 1558–2044 ms（7 次，中位约 1.77 s）。其中 native.js 的 import 占 520–560 ms，pi-sdk-runtime.js 的 import 占 975–1160 ms。RSS 约 150 MB。裸 node -e 0 是 42–47 ms，所以耗时几乎都在模块加载。
  • 证据（读代码）：每个 Rook Backend 只留 4 个 idle worker（src/chat/capacity.ts:2-6）。第 5 个活跃 Session 的用户每次回来都付一次冷启动加 MySQL 整文件恢复。
  • 对照：t3code 空闲 30 分钟才释放。Orca 30 分钟后才停。
  • 改动：
    1. 现在就能做：调大 ROOK_CHAT_MAX_IDLE_WORKERS。按 150 MB 一个算内存上限。
    2. 给 worker 设 NODE_COMPILE_CACHE。实测热缓存冷启动 1.25–1.29 s（有一次 1.68 s 的离群值），缓存目录 9.9 MB。省约 0.5 s。
    3. 3b 的 30 分钟冻结落地时加数量或内存上限。共享机器上不能只按时间留。
  • 层：executor（src/chat/isolated.ts）和部署配置。和 Runtime 无关的部分是预算数字。
  • 成本和风险：1 是配置改动，风险是内存。2 很小，但缓存目录对执行用户只读时是否生效我没有测。执行实例以不同 uid 运行，这一点必须先验证。
  • 收益：冷启动命中率没有线上数据，收益大小是推断。建议先从 RunEvent 统计 launchWorker 的次数占比。

G3. Stop 或失败后的下一个 Turn 走整文件 MySQL 恢复

  • 证据（读代码）：Run 不是 succeeded 时 isolatedExecutor 执行 delete active.checkpoint（src/chat/isolated.ts:574-575）。下一个 Turn 因此拿不到 previous，走 MySQL 整文件恢复。用户点 Stop 后马上改口重发是常见操作，这条路径正好最慢。
  • 已有的可复用路径：evicted 路径已经会懒比较本地文件和 checkpoint 的 digest（src/chat/isolated.ts:265-267，src/chat/native.ts:149-165）。
  • 改动：previous 缺失但 worker 还活着、本地文件还在时，走同一条懒比较路径。digest 一致就沿用本地文件。
  • 层：executor 加 Pi adapter 的恢复逻辑。
  • 成本和风险：小。风险是 abort 后本地文件比 MySQL checkpoint 多出未确认的行。readExtendedCheckpoint 已经处理“本地更长”的情况（src/chat/native.ts:602-623）。必须保留密钥扫描。
  • 收益：MySQL 恢复的耗时我没有测，收益大小是推断。

G4. 响应头等待实际是 120 s，重试策略比 dsh 慢

  • 证据（实测）：Pi 把 httpIdleTimeoutMs 当 provider SDK 的 timeoutMs（pi-coding-agent/dist/core/sdk.js:194-204）。探针把两个值按比例缩小：SDK 2000 ms 加 undici headers 6000 ms，请求在 2245 ms 结束，报 "Request timed out."。反过来 SDK 6000 加 undici 2000，在 2013 ms 结束。openai-completions 结果相同。所以生产的响应头上限是 min(120 s, 180 s) = 120 s。RUNTIME_CONTRACTS.md:195-199 写的 180 s 和实际不符。
  • 证据（实测）：timeoutMs 只管响应头。探针里 SDK timeoutMs 2000 ms，服务端在响应头之后持续流 6 s，请求跑满 6211 ms 才结束，没有被 2 s 截断。所以单独调小 retry.provider.timeoutMs 不会误杀长输出。
  • 证据（读代码）：RUNTIME_CONTRACTS.md:195-199 的 llmapi 采样说成功请求都在 19 s 内返回响应头，卡住的请求到 90–150 s 仍是 0 字节。Codex relay 用 60 s。
  • 证据（读代码）：Pi 重试 3 次，延迟 2 / 4 / 8 s，无 jitter。dsh 重试 5 次，500 ms 起步，上限 10 s，带 jitter，遵守 retry-after。
  • 改动：在 src/chat/pi-sdk-runtime.ts:179 的 SettingsManager.inMemory 里加 retry.provider.timeoutMs（建议 60 s，和 Codex 一致），并把 retry.maxRetries 提到 5、baseDelayMs 调到 500。同时改 RUNTIME_CONTRACTS.md 里的 180 s。
  • 层：Pi adapter，纯配置。
  • 成本和风险：很小。风险是 60 s 对个别慢模型太短。采样只覆盖 llmapi。
  • 收益：卡住的请求从等 120 s 降到 60 s。一个 Step 的最坏失败时间从约 8.2 分钟降到约 6 × 60 s + 退避 ≈ 6.3 分钟，但成功概率更高。实际能救回多少 Run 是推断。建议先用只读 RDS 查近 7 天 native_model_timeout 和 native_model_unavailable 的失败数，再决定次数。

G5. 工具没有默认超时

  • 证据（读代码）：Pi 的 bash 工具没有默认超时（pi-coding-agent/dist/core/tools/bash.js:30）。模型不传 timeout 时，一个卡住的命令会占住 Turn 直到 60 分钟上限。checkpoint 在有工具运行时还会跳过（src/chat/pi-sdk.ts:55-68）。
  • 对照：dsh 按工具强制 timeoutMs。bash 超时后转后台。
  • 改动：在 guardTools（src/chat/pi-sdk-runtime.ts:83-105）里给没带 timeout 的 bash 调用补一个默认值。Rook 已经在这里包了每个工具的 execute。
  • 层：Pi adapter。Claude Code 和 Codex 有各自的原生工具超时，不用在 Chat 层统一。
  • 成本和风险：小。风险是合法的长命令被截断。默认值要宽（例如 10 分钟），并让模型传的值优先。
  • 收益：线上有多少 native_timeout 来自卡住的工具没有查，属推断。

G6. Stop 的 15 s 超时会丢最近的 Step（和 3a 耦合）

  • 证据（读代码）：cancel 15 s 没结果，isolatedExecutor 杀 worker 并丢弃本地 JSONL（src/chat/isolated.ts:381-385, 588-589）。上次 checkpoint 之后的 Step 全丢。turn_end 的 checkpoint 有 30 s 门限（src/chat/pi-sdk.ts:97）。
  • 对照：dsh 把被中断的部分 assistant 输出带 interrupted:true 落盘。t3code 和 Orca 杀进程后 Pi 的 session 文件还在。
  • 改动：不单独做。3a 的 checkpoint 屏障和 G1 的增量 checkpoint 落地后，这个窗口自然缩到一个 Step 以内。
  • 层：Pi adapter。
  • 成本和风险：并入 3a。

G7. Queue 衔接有最多 1 s 空档
