更正：我之前说「目前没有越权」，这个说法有误。内置 Rook 是 group 可见，tools 为 *。任何能在 Task 上评论的 RD 写 @Rook，Run 就带着绑定它的管理员的 ClawSec 身份执行。DESIGN.md 已写明这一点。请求审查的 Run 不带 ClawSec 身份，普通 @Rook 的 Run 带。

决策 1：Turn 被中断后，Rook 要不要自动重发

中断指 Pod 重启、发布 drain、租约丢失或模型请求卡住。Chat 现在把 Turn 记为失败，由用户手动重发。自动重发的风险是重复执行中断前已经发生的工具调用，比如写文件或调用连接器。

同类产品

产品中断后的行为标注
t3code服务重启后默认在原会话发一条「继续」，要求模型先确认有副作用的操作是否已生效。5 分钟内最多 3 次。provider 还没接收 prompt 时，用户消息留给用户处理，定时任务的 prompt 自动重发。实测
Orca应用重启后发「先检查最近的操作是否完成，完成了就不要重复」。每个中断的 Turn 有「继续」按钮，界面注明原 prompt 未重发。实测
Multica（开源项目）runtime 离线或断流时自动重试 2 到 3 次，不看工具是否已执行。面向无人值守的 issue 任务。实测
dsh给未完成的工具补一条结果「结果未知，只在只读或幂等时重试」，Turn 以 interrupted 结束，不自动续。实测
Claude Code进程意外退出后自动重启会话，发「从中断处继续，先复核」。未完成的工具补「outcome is unknown」。推断（二进制字符串）
Codex下一轮注入 turn_aborted，提示工具可能已部分执行。推断（二进制字符串）

Cursor、Copilot、Claude Code on the web停在空闲或失败状态，等用户发下一条消息或重新指派。实测（官方文档）

托管产品的官方文档都没有写「自动重发整个任务」。共同做法是：工具开始前可以安全重做，工具开始后只发一条先核对再继续的消息，或者交给用户。

Rook 现状

  • 两个 Turn 之间回收常驻进程，下一轮从 MySQL 恢复，用户无感。实测
  • Turn 中途遇到 Pod 重启或租约丢失，Run 记为 interrupted。还有未结束的工具时记为 execution_tool_result_unknown。实测
  • 自动化任务、智能体 Task 和私聊已经在「还没开始任何工具」时重投一次，但只对 Pi 生效。Codex 和 Claude Code 只统计了定时工具，这个计数不可用。实测
  • Codex 和 Claude Code 只在 Turn 成功时保存原生 context。中断后再发「继续」，模型看不到中断前做过的事。实测

选项

A. 按工具是否开始分两段推荐
  • 工具开始前：自动重发原 prompt 一次，按 requestId 去重。复用后台任务已有的逻辑，没有重复执行的风险。
  • 工具开始后：不自动处理。Pi 上给「继续」按钮，发一条先核对再继续的消息，因为 Pi 的 checkpoint 里有中断前的工具结果。Codex 和 Claude Code 只显示提示，让用户核对后自己重发。
  • Codex 和 Claude Code 要先统计全部工具的开始（Codex 的 item/started，Claude Code 的 tool_use），之后才能启用第一段。
  • 成本：小到中。
B. 维持现状，只补提示文案
  • Web 端给 service_interrupted、execution_tool_result_unknown 写明确的提示。成本接近零。用户每次都要自己判断。
C. 像 t3code 一样默认自动继续
  • Codex 和 Claude Code 需要 Turn 中途的 checkpoint。重复执行的风险全靠模型自查。ClawSec 连接器调用没有幂等键，模型可能无法确认操作是否已生效。成本高。

决策 2：智能体用谁的凭据，白名单在哪里生效

每个智能体 Run 的进程 env 里都有 owner 的 SSO。模型可以直接读出 token 调 ClawSec 网关，所以在 Runtime 内过滤命令一定能被绕过。Claude Code 的官方文档也说按参数匹配 Bash 的规则容易绕过。

同类产品

产品运行身份拦截点模型能否读到凭据
GitHub App、Copilot、OpenHandsApp 自己的身份，令牌按仓库和权限收窄，短期过期GitHub 服务端能，但令牌本身范围小
Slack、Linearbot 自己的身份，由管理员安装平台服务端的 scope不适用

Devin组织 secret 全员可用，个人 secret 只用于本人；建议给 Devin 单独开账号无服务端 scope能
Orcaowner（「every bot runs as the owner」）宿主机的 relay 按 bot 附加凭据不能
Multica（开源项目）runtime owner进程内，强制跳过权限能

对多人开放的产品只有两种做法。一种是 bot 用自己的身份，在服务端收窄范围。另一种是用触发者自己的身份。像 Rook 这样把创建者的凭据放进别人能触发的沙箱，只有 Multica 这样做。MCP 规范也明确禁止把令牌原样转发给下游。

选项

A. 内置 Rook 的 Run 不带 ClawSec 身份推荐，现在做
  • 内置 Rook 的指令写明「只用当前需求提供的材料」「保持外部系统不变」，它本来就不需要连接器。请求审查的 Run 已经这样处理，普通 @Rook 照同样处理。
  • 改动小，立刻消除现有的借权问题。
  • 代价：有人如果靠 @Rook 查外部系统，这个用法会失效。我没有核实是否有人这样用。
  • 普通用户开放创建 group 智能体时，再从 B 和 C 里选。在那之前 group 仍只有管理员能设。
B. group 智能体改用触发者自己的 SSO
  • 照 Cursor 的做法。个人智能体和定时器继续用 owner。借权问题直接消失，tools 只用来收窄范围。
  • 成本：Task 会话要按触发者拆分，因为原生 context 里有用别人权限取到的结果。一个批次只能来自同一个触发者。需要触发者有有效的 SSO 会话。
  • 依赖 claw-sec 的 skill 照常可用，身份换成触发者。
C. 智能体用数字员工身份，owner 按 tools 出借连接
  • 和 GitHub App、Slack 一样，范围由 ClawSec 服务端拦截。ClawSec 的连接上有 allowedActions，超范围返回 scope_denied；借用的 --scope 是否同样生效，还没有实测。
  • 成本：每个智能体一个数字员工账号，每个连接器走一轮借用审批。依赖个人 SSO 直连公司服务的 skill 可能被拒。

不推荐由 Rook Backend 代发连接器调用。ClawSec 本身就是 broker，再做一层等于重写网关。依赖真实凭据的 skill 也拦不住。

没有核实的

  • Codex app-server 中断恢复的结论只来自二进制字符串。
  • ClawSec 借用 --scope 能否按操作限制，没有调用借用或写操作。
  • 是否有人依赖 @Rook 访问外部系统。
